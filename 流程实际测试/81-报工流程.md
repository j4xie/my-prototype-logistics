# 81. 报工流程 (⭐ 核心流程 - 最高频)

**来源**: 六扇门 Mar 18 会议 + Apr 7 v3 需求
**核心原话** (张权):
> "核心逻辑还是扫码嘛, 扫码扫人扫工序报上来"
> "以订单的模式去呈现的, 清晰记录每批订单里面, 每道工序里面的投入产出跟人工工时"
> "一个产品有十个工序, 在于说这十个工序怎么分析"

**耗时**: 60-90 min 端到端
**涉及模块**: §06 生产 + §23 批次 + §20 质检 + §10 跨模块 + §50 BI

---

## 81.1 流程总览

```
[Web 计划] 生产计划指派 operator
    ↓
[RN 扫码] operator 扫工牌 + 扫工序 QR
    ↓
[RN 报工] 录入投入 (原料消耗) + 产出 (完工数量) + 工时
    ↓
[Web 审批] foreman 审批通过
    ↓
[数据同步] 批次状态更新 + 库存扣减 + 工时累计
    ↓
[BI 分析] 订单 × 产品 × 工序 三维达成率 / 效率 / 成本
```

## 81.3 Step-by-Step

### Step 1: Web 创建生产计划 + 指派
1. 登 admin → `/production/plans` → 新建
2. 关联 SO-xxx, 选 产品 / 批次号 / 计划数量 / 工序链
3. 指派 operator1 (员工号 E001)
4. **预期**: 计划状态 READY, operator RN "工作" Tab 看到新任务

### Step 2: RN 扫码报工 (operator 核心)
1. RN 登 operator1 → "工作" Tab → 点任务
2. **扫工牌 QR** → 自动填 员工号 E001
3. **扫工序 QR** → 自动填 工序 (如"切配")
4. 录入:
   - 投入量 (原料): 预计 100, 实际 101 → 达成率 99%
   - 产出量 (成品): 计划 50, 实际 48 → 达成率 96%
   - 工时: 开始/结束时间 (自动) 或手填
   - 异常备注 (可选)
5. 拍照附件 (可选 §08)
6. 提交 → 状态 PENDING_APPROVAL

### Step 3: 离线兜底 (若网络断)
- RN 本地 AsyncStorage 存草稿
- 联网自动同步 (§09)
- **冲突**: 返回 409 → "数据已更新, 请刷新后重做"

### Step 4: Web foreman 审批
1. Web 登 foreman → `/production/approval`
2. **3s 内** 看到 operator 新报工
3. 审批通过 / 驳回 (驳回需备注)
4. **预期**: RN operator 收推送 3-5s "您的报工已通过"

### Step 5: 后端数据联动 (自动)
批次 `BATCH-xxx` 状态 → IN_PROGRESS → COMPLETED
原料库存扣减 (动态库存, 见 §85)
写入 `production_reports` 真实字段:
- `production_start_time` / `production_end_time` (LocalTime)
- `total_work_minutes` (Integer, 工时 = 结束 - 开始)
- `output_quantity` / `good_quantity` / `defect_quantity` (BigDecimal, 产出/良品/不良)
- 达成率通过 `goodQuantity / plannedQuantity` 计算 (非独立字段)
成品入库 (若是末道工序)

### 跨端同步要求 (对齐 `移动端流程测试/14.2`)
| 链路 | 延迟 | 通道 |
|------|------|------|
| RN 报工提交 → Web `/production/approval` 列表 | **5-10s** (轮询) 或手动下拉刷新即时 | 轮询 |
| Web foreman 审批 → RN 推送 | 3-5s | WebSocket / 推送 |
| 并发冲突 (foreman 同时改) | 返回 409 | 乐观锁 rowVersion |

**注**: "3s 内"是理想值 (推送通道), 真实轮询基线是 5-10s, 与 §14.8 统一.

### Step 6: BI 三维分析
1. Web `/smart-bi` → "订单达成率分析"
2. **三维聚合**:
   - **订单维度**: SO-xxx 整体达成率 96%
   - **产品维度**: 产品 A 投入产出比 1.01
   - **工序维度**: 切配工序效率 vs 历史均值
3. AI 分析 (LLM): "SO-xxx 在切配工序出现 1% 物料超耗, 建议检查切配设备磨损"

## 81.5 异常场景

| 场景 | 预期行为 |
|------|---------|
| 工序 QR 损坏 | 手动选择兜底 |
| 员工工牌丢失 | 主管代录 + 签字 |
| 投入远超 BOM (> 20%) | 强制备注异常原因 |
| 产出为 0 | 标记工序失败 + 转异常处理 |
| foreman 离开审批超 2h | 升级通知车间主任 |
| 批次在其他工序报废 | 本工序无法继续报工 |

## 81.6 数据埋点 (观测)

- `production_reports`: 每次报工 1 行 (真实字段见上)
- `material_batches`: 批次状态 + 扣减
- `batch_status_history`: 批次状态流转日志
- `approval_logs`: 审批全链路 (PENDING → APPROVED/REJECTED)

**注**: 无独立 `labor_hours` 表, 工时用 `production_reports.total_work_minutes`.
无独立 `yield_rate` 字段, 达成率 = `good_quantity / planned_quantity` 动态算.

查询:
```sql
SELECT sr.order_id, sr.product_id, sr.process_id,
  AVG(sr.yield_rate) AS 达成率
-- 三维达成率 (订单 × 产品 × 工序)
-- 注: production_reports 无 planned_quantity 字段, 需 JOIN production_plans 或 process_tasks
SELECT pp.sales_order_id AS order_id, pp.product_id, sr.process_id,
  SUM(sr.good_quantity) / NULLIF(SUM(pp.planned_quantity), 0) AS 良品达成率
FROM production_reports sr
JOIN production_plans pp ON sr.production_plan_id = pp.id
WHERE sr.factory_id = ?
GROUP BY ROLLUP(pp.sales_order_id, pp.product_id, sr.process_id);

-- 工时汇总 (分钟)
SELECT sr.operator_id, SUM(sr.total_work_minutes) / 60.0 AS total_hours
FROM production_reports sr
WHERE sr.factory_id = ? AND sr.created_at BETWEEN ? AND ?
GROUP BY sr.operator_id;
```

## 81.7 演示话术 (给六扇门看)

> "扫码扫人扫工序报上来" — 张权原话. 我们把这句话落成产品:
> 1. operator 上工位, 一扫工牌 (E001), 二扫工序 QR (切配), 系统秒识别身份+工位
> 2. BOM 预填 "预计投入 100kg", 实际用了 101kg 直接录, 系统算达成率 99% / 超耗 1%
> 3. 3 秒内 foreman 电脑上看到这条报工, 一键通过 → operator 手机收推送
> 4. 数据自动进 BI 三维分析: "SO-xxx 的产品 A 在切配工序超耗 1%, 建议检查设备" — 这就是您说的"拆到工序"

**客户常问**:
- "10 道工序怎么拆?" → 每道工序独立报工, 系统按 order_id × product_id × process_id ROLLUP 聚合
- "超耗报警吗?" → >5% 红色告警, >10% 强制备注异常原因
- "离线怎么办?" → RN 本地草稿, 联网自动同步 (§09)

## 81.8 通过标准

- **端到端无断点**: Web 计划 → RN 报工 → Web 审批 → 库存 → BI, 每环节数据一致
- **达成率准确**: 投入/产出/工时三项计算对上 BOM
- **三维可追溯**: 订单/产品/工序任何维度都能下钻到单次报工
- **AI 分析有效**: LLM 给出有业务意义的建议 (非空话)
- **25/25 checklist 全过** (100%)
