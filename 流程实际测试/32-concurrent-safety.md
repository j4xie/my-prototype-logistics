## 32.3 同用户 2 标签页同编辑 (最高频)

### 步骤
1. 标签页 A 打开 SO 详情 → 点 "编辑"
2. 标签页 B 打开**同 SO** 编辑
3. A 改单价 50 → 保存 → 成功
4. B 改数量 100 → 保存

### ✅ 期望 (乐观锁)
- B 保存时后端返 **409 Conflict**
- 前端提示: "**数据已被修改, 请刷新重试**"
- B 点刷新 → 看到 A 的修改 → 再改 → 保存成功

### ❌ FAIL
- B 悄无声息覆盖 A 的修改 (数据丢失)
- 两个版本都保存了 (脏数据)

### 检查后端
- 实体含 `rowVersion` 字段
- UPDATE 时 WHERE rowVersion = {original}

## 32.4 2 账号并发同一 SO

### 场景
- 窗口 1: sales 编辑 SO
- 窗口 2: finance 打开同一 SO 准备审核

### 测试
1. sales 改单价 50 → 保存 → 成功
2. finance 基于旧值审核通过

### ✅ 期望
- finance 刷新能看到新单价
- 或 sales 保存触发 finance 页实时更新 (WebSocket)
- 最低要求: 数据库最终一致

## 32.5 A 审核 B 改字段

### 场景
- A (finance): 正在 SO 详情页审核
- B (sales): 此时 edit 订单修改数量

### 规则 (业务)
- SO 状态 PENDING_FINANCE_REVIEW 时**应锁定**, 不允许 sales 改
- ✅ 如果已锁, B 的编辑按钮 disabled / 不可见
- ❌ 如果没锁, 容易发生 A 基于旧数据审, B 修改导致审核过的是"假数据"

## 32.6 并发开票同一 SO ⭐

### 场景
- SO 金额 5000
- A 窗口点一键开票 → LLM 正生成 2 张发票
- B 窗口同时也点一键开票 (快速) → LLM 又生成 2 张

### ✅ 期望
- 后端幂等处理: 只生成一组发票 (以 SO+session 为 key)
- 或前端防抖: A 点击后按钮 disabled, B 用户看到 "正在生成, 请稍后"

### ❌ FAIL
- 生成 4 张发票 (重复)
- 金额叠加 = 2× SO

## 32.7 并发发货扣批次

### 场景 ⭐ 高风险
- 成品库存批次 A = 50 kg
- 发货单 1 要 30 kg (A batch)
- 发货单 2 要 30 kg (A batch)
- 同时 "确认发货"

### 期望
- 后端**乐观锁** or **悲观锁** 保证不超扣
- 一个成功, 另一个报 "库存不足"
- 最终: batch A 剩 20 (或 -10 如果 bug)

### 测试
1. 2 窗口并发点 "确认发货"
2. 检查 batch A 数量

### ❌ FAIL
- 两个都成功, batch A 变 -10 (严重 bug, 数据库无约束)

## 32.10 并发登录同账号

### 场景
- A 窗口登 admin
- B 窗口也登 admin

### 期望 (按策略)
- 策略 A: 允许多点登录 (都能用)
- 策略 B: 后登入把前登 kick 掉 (前提示 "已在其他设备登录")

### 测试
- 检查 JWT 是否共享还是各有 token
- B 登陆后 A 的 token 是否失效
