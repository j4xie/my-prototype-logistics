## 1. 目标与边界

### 1.1 目标

多个文件给同一字段不同值时, 系统**自动选最优值**, 派生 KPI 标注**置信度 + 来源**, 客户审计可追溯.

3 个层次:

1. **Cell-level Provenance**: 每个 entity 的每个字段记录 "来源 + 时间 + 置信度", 不再是表级 upload_id
2. **冲突解决规则**: 多源同字段不同值时, 按优先级 + 时间窗 + 客户裁决决定权威值
3. **继承 Cascade**: 长期属性 (配方成本) 自动应用到动态记录 (销售) 派生指标 (毛利)

### 1.2 在 Data Fabric 体系中的角色

```
B 完成 (entity_id 稳定, merge_status 简单)
       ↓
[C] field_provenance 表 (cell-level)        ← 本 spec
       ↓
[C] 冲突解决规则 + 优先级                    ← 本 spec  
       ↓
[C] 继承 Cascade (配方→销售→毛利)            ← 本 spec
       ↓
[C] Trust Indicator UI                       ← 本 spec
       ↓
[C] B 的 merge_status → field_provenance 升级 ← 本 spec
       ↓
D Federated Query 消费 confidence cascade
```

### 1.3 in-scope vs out-of-scope

**In Scope**:

### 2.1 完整 DDL

```sql
-- migration: 2026_04_25_field_provenance.sql

CREATE TABLE field_provenance (
    id BIGSERIAL PRIMARY KEY,
    factory_id VARCHAR(50) NOT NULL,
    
    -- 实体引用 (polymorphic, 不强制 FK 因为支持多种 entity)
    entity_type VARCHAR(30) NOT NULL,    -- 'store' / 'product' / 'staff' / 'bill' / 'finance_voucher' / 等
    entity_id BIGINT NOT NULL,           -- 对应 dim_*/fact_* 的 PK
    
    -- 字段定位
    field_name VARCHAR(100) NOT NULL,    -- canonical 字段名 (从 _ALIAS_TO_ATTR)
    
    -- 字段值 (polymorphic via JSONB)
    field_value JSONB NOT NULL,          -- 数字/字符串/数组都装
    
    -- 来源
    source_upload_id BIGINT REFERENCES smart_bi_pg_excel_uploads(id) ON DELETE SET NULL,
    source_type VARCHAR(50),             -- 'bill_flow' / 'product_summary' / 'review' / 'manual' / 'inferred' / 'industry_default'
    source_priority INT,                 -- 1 (最高: 客户手动) ~ 6 (最低: 行业默认), 见 §3

    valid_to DATE,                       -- NULL 表示无上界

    created_by VARCHAR(50),              -- 'system' / 'admin:<username>' / 'writer:<class>'
```

### 2.2 polymorphic field_value 设计

`JSONB` 装任意类型, 上层 reader 按 field_name 解读:

```python
# 字段类型推断 (从 ALIAS_TO_ATTR 元数据扩展)
FIELD_TYPE_MAP = {
    "store_name": "string",
    "date": "date_string",
    "gross_amount": "decimal",
    "customer_count": "int",
    "rating": "decimal",
    "top_keywords": "string_array",
    # ...
}

def read_field_value(provenance_row) -> Any:
    raw = provenance_row["field_value"]  # JSONB
    field_type = FIELD_TYPE_MAP.get(provenance_row["field_name"])
    if field_type == "decimal":
        return Decimal(raw["v"])  # JSONB stored as {"v": "12.34"}
    elif field_type == "date_string":
        return date.fromisoformat(raw["v"])
    # ...
```

JSONB 让我们**不需要按类型分多张表**, 同时保持 SQL-queryable.

## 3. 冲突解决规则

### 3.1 优先级表

`source_priority` 取值 (低数字 = 高优先级):

| Priority | source_type | 含义 | 例子 |
|---|---|---|---|
| 1 | `manual` | 客户手动确认/修改 | admin UI 改 product.cost = 60 |
| 2 | `bill_flow` | 官方 POS 账单流水 | 现成 backfill_silver.py |
| 3 | `product_summary` | 商品销售汇总 | xmx 报表 |
| 4 | `review` / `external_platform` | 第三方平台 | 大众点评导出 |
| 5 | `inferred` | AI 推断 | LLM 抽 keyword |
| 6 | `industry_default` | 行业默认值 | 川菜成本率 0.35 |

### 3.2 解决算法

```python
# backend/python/smartbi/canonical/provenance/resolver.py
async def get_authoritative_value(
    factory_id: str, entity_type: str, entity_id: int, 
    field_name: str, as_of_date: Optional[date], pool
) -> Optional[ProvenanceValue]:
    """取某 entity 某 field 在指定日期的权威值.
    
    规则:
    1. 过滤 superseded_by_id IS NULL (活跃记录)
    2. 过滤 valid_from <= as_of_date AND (valid_to IS NULL OR valid_to >= as_of_date)
    3. 按 source_priority ASC, confidence DESC, created_at DESC 排序, 取 top 1
    """
    async with pool.acquire() as conn:
        row = await conn.fetchrow("""
            SELECT * FROM field_provenance
             WHERE factory_id = $1
               AND entity_type = $2
               AND entity_id = $3
               AND field_name = $4
               AND superseded_by_id IS NULL
               AND (valid_from IS NULL OR valid_from <= $5)
               AND (valid_to IS NULL OR valid_to >= $5)
             ORDER BY source_priority ASC, confidence DESC, created_at DESC
             LIMIT 1
        """, factory_id, entity_type, entity_id, field_name,
            as_of_date or date.today())
    return ProvenanceValue.from_row(row) if row else None
```

### 3.3 30% 差异自动弹审

新写入的 field_value 与现有最高优先级值 **数值差异 > 30%** 时, 不直接 supersede, 而是写入 `entity_resolution_admin_queue`:

```python
async def write_field_provenance_with_conflict_check(
    factory_id, entity_type, entity_id, field_name, new_value, source, ...
) -> dict:
    """写 provenance 时检查冲突. 差异 > 30% → 进 admin queue 不直接覆盖.
    
    Returns: {"action": "written" | "queued" | "no_change"}
    """
    async with pool.acquire() as conn:
        # 1. 取现有最高优先级值
        current = await get_authoritative_value(factory_id, entity_type, entity_id, field_name, None, conn)
        
        if current is None:
            # 没现有, 直接写
            await _insert_provenance(conn, ...)
            return {"action": "written"}
        
        # 2. 数值字段才比对差异 (字符串字段直接覆盖低优先级)
        if FIELD_TYPE_MAP.get(field_name) in ("decimal", "int") and current.value != 0:
            diff_ratio = abs(new_value - current.value) / abs(current.value)
            if diff_ratio > 0.30 and source_priority >= current.source_priority:
                # 差异大且不是更高优先级 → admin 队列
                await _queue_for_admin_field_conflict(
                    conn, factory_id, entity_type, entity_id, field_name,
                    current_value=current.value, new_value=new_value,
                    diff_ratio=diff_ratio
                )
                return {"action": "queued"}
        
        # 3. 正常写入 + supersede 旧值 (如果优先级更高)
        if source_priority < current.source_priority:
            await conn.execute(
                "UPDATE field_provenance SET superseded_by_id = $1, superseded_reason = 'higher_priority' WHERE id = $2",
                new_id, current.id
            )
        await _insert_provenance(conn, ...)
        return {"action": "written"}
```

### 3.4 时间窗规则

同字段多个值时间窗**不重叠** → 各自负责自己时段, 都活跃:

```
配方 v1: cost=60, valid_from=2025-01-01, valid_to=2025-06-30
配方 v2: cost=70, valid_from=2025-07-01, valid_to=NULL

查询 2025-03 销售毛利 → 用 v1 (cost=60)
查询 2025-09 销售毛利 → 用 v2 (cost=70)
```

时间窗**重叠** → 取最新 created_at, 旧的标 `superseded_by_id` (除非新的优先级更低, 那种 case 罕见但需正确处理).

## 4. 继承 Cascade Engine

### 4.1 5 类继承

| 类型 | 例子 | 实现 |
|---|---|---|
| **维度继承** | 配方 (静态) → 所有时段销售自动算毛利 | LEFT JOIN field_provenance |
| **时间继承** | 账单流水有日期 → 同月商品汇总借用日期窗 | Sheet Merger merge_inferred_period_* + cascade |
| **粒度继承** | 月级商品汇总 ← 日级账单流水 (升精度) | aggregate-on-read 视图 |
| **属性继承** | 菜品标"川菜" → 所有该菜销售带"川菜" | dim_product.tags JSONB |
| **空缺降级** | 该菜无配方 → 用行业平均成本率 | source_priority=6 industry_default |

### 4.2 继承示例: 配方 → 销售毛利

```python
# backend/python/smartbi/canonical/provenance/cascade.py
async def compute_dish_margin(
    factory_id: str, product_id: int, date_range: tuple[date, date], pool
) -> dict:
    """计算菜品毛利, 自动 cascade 配方成本.
    
    Steps:
    1. 取 product_id 的 cost_per_unit (from field_provenance, 时间窗匹配)
    2. 取 product_id 在 date_range 的销售 (from agg_product_period 或 fact_pos_item)
    3. 算毛利 = revenue - cost * qty
    4. 返回带 confidence (cost 的 confidence + sales 的 confidence)
    """
    async with pool.acquire() as conn:
        # 1. cost (时间窗匹配)
        cost_prov = await get_authoritative_value(
            factory_id, "product", product_id, "cost_per_unit",
            as_of_date=date_range[1], pool=conn  # 用结束日期取
        )
        if cost_prov is None:
            # 空缺降级到行业默认
            cost_prov = await _get_industry_default_cost(factory_id, product_id, conn)
        
        # 2. sales
        sales = await conn.fetchrow("""
            SELECT SUM(revenue) AS total_rev, SUM(qty_sold) AS total_qty
              FROM agg_product_period
             WHERE factory_id = $1 AND product_id = $2
               AND period_start >= $3 AND period_end <= $4
        """, factory_id, product_id, date_range[0], date_range[1])
        
        # 3. 算毛利
        revenue = float(sales["total_rev"] or 0)
        qty = float(sales["total_qty"] or 0)
        cost_per_unit = float(cost_prov.value)
        margin = revenue - (cost_per_unit * qty)
        margin_rate = margin / revenue if revenue else 0
        
        # 4. 综合 confidence
        # margin confidence = min(cost confidence, 1.0) — sales 假定 100% (来自 fact)
        result_confidence = cost_prov.confidence
        
        return {
            "product_id": product_id,
            "revenue": revenue,
            "cost": cost_per_unit * qty,
            "margin": margin,
            "margin_rate": margin_rate,
            "confidence": result_confidence,
            "cost_source": cost_prov.source_type,  # 让 UI 显 "[配方表] / [行业默认]"
        }
```

### 4.3 时间继承示例: 账单 → 商品汇总

```python
async def infer_product_summary_period(
    factory_id: str, product_summary_upload_id: int, conn
) -> Optional[tuple[date, date]]:
    """商品汇总没日期, 但同 factory 同时段有账单流水 → 借用账单时间窗.
    
    Steps:
    1. 取 product_summary upload 的 created_at (上传时间)
    2. 找同 factory 同 ±7 天上传的 bill_flow upload
    3. 取它们的 merge_inferred_period (来自 B Sheet Merger)
    4. 求并集作为推断时间窗
    """
    upload_date = await conn.fetchval(
        "SELECT created_at::date FROM smart_bi_pg_excel_uploads WHERE id = $1",
        product_summary_upload_id
    )
    
    # 同 factory ±7 天的 bill_flow upload
    bill_uploads = await conn.fetch("""
        SELECT merge_inferred_period_start AS p_start,
               merge_inferred_period_end AS p_end
          FROM smart_bi_pg_excel_uploads
         WHERE factory_id = $1
           AND detected_table_type = 'bill_flow'
           AND created_at::date BETWEEN $2::date - 7 AND $2::date + 7
           AND merge_inferred_period_start IS NOT NULL
    """, factory_id, upload_date)
    
    if not bill_uploads:
        return None  # 没邻近账单, 时间继承失败
    
    # 求并集
    return (
        min(b["p_start"] for b in bill_uploads),
        max(b["p_end"] for b in bill_uploads),
    )
```

## 5. B merge_status → field_provenance 升级 path

### 5.1 兼容性策略

B 阶段加 `smart_bi_pg_excel_uploads.merge_status` 列做简单覆盖标记. C 上线后:

1. **保留 merge_status 列** (向后兼容, A 的 capability calculator 仍读它)
2. **新增 field_provenance 表** (cell-level)
3. **双轨过渡期**: B 的 writer 同时写 merge_status (upload 级) + field_provenance (cell 级) ~ 2 周
4. **A 的 calculator** 可选查询 field_provenance 算 capability (但不强制)
5. **D 的 query planner** 优先用 field_provenance 的 confidence

### 5.2 双写迁移

```python
# C 阶段升级 B 的 ProductSummaryWriter
class ProductSummaryWriter(BaseWriter):
    async def write(self, upload_id, factory_id):
        # ... B 原有逻辑 (写 agg_product_period) ...
        
        # v1.0 (C 阶段加): 同时写 field_provenance
        for record in records:
            await self._write_provenance_for_record(record)
    
    async def _write_provenance_for_record(self, record):
        """每行 record 拆成 N 个 cell-level provenance 行."""
        for field_name, value in record.fields.items():
            await write_field_provenance_with_conflict_check(
                factory_id=record.factory_id,
                entity_type="product",  # 或 store, 看 field
                entity_id=record.product_id,
                field_name=field_name,
                new_value=value,
                source=ProvenanceSource(
                    upload_id=record.upload_id,
                    source_type="product_summary",
                    source_priority=3,
                    confidence=0.85,
                    confidence_method="rule",
                ),
                valid_from=record.period_start,
                valid_to=record.period_end,
            )
```

### 9.1 真实规模

|---|---|---|

| `dim_store` | 149 | 同上 |

### 9.2 4-Phase 回填 (从 roadmap §11.5 继承 + 细化)

```
Phase 1 (Day 11-12): Schema migration + Test 环境验证
  - field_provenance 表上线 (空)
  - Test 环境 (cretas_db, ~10K 行) 跑完整 backfill 验证脚本
  - 不影响现有读路径

Phase 2 (Day 13-14): Prod 后台批量回填
  - 优先级: dim_* (小表, 快) → fact_pos_transaction → fact_pos_item
  - Batch size: 5,000 行/批 (S-4 同尺度)
  - sleep 200ms/批 防拖慢 prod
  - 用 SKIP LOCKED 避免阻塞写入
  - 预估时间: 1.31M / 5K × (200ms + 50ms write) = ~65 分钟 (后台)
  - 监控: pg_stat_replication 复制延迟

Phase 3 (Day 15): 双写过渡期开始
  - B 的 writer 同时填 fact + provenance
  - 老 reader 仍读 fact (兼容)
  - 新 reader (Trust UI) 读 provenance
  - 一致性 verify: 随机抽 1000 行检查 fact.value == provenance.field_value

Phase 4 (Day 22+): cutover  
  - field_provenance 成为权威源 for Trust UI + D 的 query planner
  - 老 reader 路径保留兼容性 (永远不删, 防 regression)
```

### 9.3 风险控制

- **rollback 计划**: drop field_provenance 表 + 删迁移记录, 不影响现有数据 (双写过渡期数据在 fact 表里)
- **Prod 跑前**: pg_dump 备份 fact_pos_* (~600MB)
- **监控指标**: 复制延迟 / active connections / lock waits / disk usage (provenance 表预计 +500MB)

## 10. 风险与未决问题

### 10.1 风险

| # | 风险 | 缓解 |
|---|---|---|
| C1 | field_provenance 表 3-4M 行查询变慢 | 索引设计 (idx_fp_active_value 是 partial index `WHERE superseded_by_id IS NULL`) + 月度 vacuum |
| C2 | 回填阻塞 prod | Phase 2 sleep 200ms/批 + SKIP LOCKED + 凌晨跑 |
| C3 | 双写期一致性失败 (fact != provenance) | Phase 3 一致性 verify 脚本, 不一致 → P0 incident |
| C4 | 30% 差异阈值过严/过宽 | 上线后调, basic 30% / enterprise 可配 |
| C5 | 优先级表客户分歧 (客户认为 review 优先级应高于 product_summary) | UI 加 admin 配置, factory-specific 覆盖 |
| C6 | B 的 merge_status 升级期间 capability 短暂不一致 | A v1.4 §13 BU6 已知, C Phase 3 期间监控 |
| C7 | LLM provider 宕机时 industry_default 也得来自 LLM (空缺降级失败) | hardcoded 行业默认表 (川菜 0.35 / 火锅 0.28 / 等) 不依赖 LLM |
| C8 | RLS 性能 (3-4M 行加 RLS check 拖慢查询) | partial index 把 RLS 过滤前置 + EXPLAIN 验证 |

### 10.2 未决问题 (送审用户)

1. **30% 差异阈值是否合理**: 太严格 → admin 队列爆炸. 太宽 → 数据被静默覆盖. 建议 basic=30%, enterprise 可配 10-50%.

2. **优先级表是否客户可调**: 不同客户偏好不同 (例如餐饮看重 review 评分, 工厂看重 ERP 准确度). 加 admin 配置页?

3. **industry_default 表来源**: 内部 hardcode (基于行业经验) vs 客户上传配置 vs LLM 生成. 倾向 hardcode + 客户可覆盖.

4. **field_provenance 月度 vacuum 时机**: 每月 1 号凌晨? 客户低峰? 还是 Postgres autovacuum 自动处理?

5. **superseded 历史保留多久**: 永久 (可审计) vs 90 天后归档 (省空间). 建议永久, 因为 3-4M 行再 superseded 翻倍也才 8M, 不是大问题.
