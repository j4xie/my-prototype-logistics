# 数据织网 (Data Fabric) — 总览路线图

**版本**: v1.0
**日期**: 2026-04-25
**作者**: 项目组
**状态**: 待评审

---

## 摘要

本文档定义了 Cretas 餐饮 SaaS 系统升级为**多源数据融合 + AI 实体解析 + 联邦查询**架构 (业界称 Data Fabric / MDM) 的整体路线图. 目标: 客户上传**任何格式**的餐饮业务文件, 系统自动识别 → 解析 → 融合 → 分析, 不依赖单一数据源, 不强制客户改变工作流.

**关键数字**:
- 当前已具备约 **60%** 基础能力 (5 张 dim 表 / 4 张 fact 表 / 3 张 agg 表 / 44 个分析模板 / 字段映射注册表 / RLS 多租户隔离)
- 待补齐 **4 块拼图**: 能力驱动渲染 / 实体解析 + 形态路由 / 字段血统 + 继承 / 联邦查询引擎
- 总工作量 **5-8 周**, 拆为 4 个独立可交付 Sub-Project (A/B/C/D)
- 完成后实现 **88-90% 数据形态覆盖** (剩余 10-12% 需上游补数据)

## 1. 战略背景

### 1.1 客户痛点 (Why)

中小餐饮连锁 (10-200 家门店) 面临**数据碎片化**:
- 不同门店用不同 POS 系统 (历史并购/品牌差异)
- 总部 ERP / 供应链 / 人事 是另一套
- 大众点评 / 美团 / 抖音外卖 数据是平台导出
- 财务在金蝶 / 用友
- 各系统**字段不同 / 命名不同 / 粒度不同**

商家想看"昨天哪家店哪道菜亏钱了" 这种简单问题, 现实是要打开 6 个系统手工拼数据. 已有 BI 工具假设客户用单一 POS, 现实根本不成立.

### 1.2 行业现状 (What's Out There)

调研基于 2026-04 公开资料:

| 厂商 | 强项 | 缺什么 (我们的机会) |
|---|---|---|
| **Snowflake Cortex Code** (2025-11 上线, 2026-04 升级) | "agentic enterprise", LLM 跨数据栈编排 | 通用产品, 餐饮场景需深度定制; 年费数十万美元, SMB 用不起 |
| **Databricks Unity Catalog** (2026-04 加 AI_parse_document) | 文档→表 AI 抽取已商业化 | 同上, 通用 + 贵 |
| **Salesforce Data Cloud** | Identity Resolution 商业化 | 专攻客户数据 (CDP), 不做餐饮业务实体 |
| **Atlan / Alation** | Data Catalog + Provenance | 只做元数据, 不做查询 + 分析 |
| **阿里 Dataphin** | MDM + 数据治理, 主打金融政府 | 年费 50万+, 餐饮 SMB 用不起 |
| **客如云 / 二维火 / 哗啦啦 / 美味不用等** (中国餐饮 SaaS) | POS 主战场已成红海 | **数据分析弱, 多源融合几乎没有, AI 极少** |
| **美团 To B / 阿里口碑** | 流量 + 数据 | 商家不愿绑死, 拒绝则数据无法迁出 |

**全球共同盲点**: 没有一家**真正解决"商家有 N 种格式碎片化数据"问题**. 大厂工具贵且通用, 小厂 SaaS 锁定单一 POS. 我们的位置在两者之间.

### 1.3 LLM 实体解析的 SOTA

2025-2026 学术 + 工业界进展:

| 技术 | 准确率 | 成本 | 适用场景 |
|---|---|---|---|
| Multi-Agent RAG (Preprints.org 2025-10) | 94.3% (姓名变体), -61% LLM 调用 | 中 | **我们采用** |
| Embeddings + Fuzzy + Deterministic (主流) | 90-95% | 中 | baseline, 易实现 |
| Probabilistic Record Linkage with embeddings (Cambridge 2025) | 88-92% | 低 | 可作为简化版 baseline |
| fuzzylink (开源) | 85-90% | 极低 | 算法参考 |

**关键洞察 (论文 + 工程双重验证)**: "Embedding **结构化上下文**而不是裸名字" 准确率提升最大. 例: 店名 + 城市 + 区 + 品牌 一起 embed, 比只 embed 店名准确率高 8-15%.

### 1.4 我们的战略定位

> **不抢 POS 主战场, 做"任何餐饮商家的多源数据融合 + AI 分析"层**.

3 条防御:
1. **垂直深度**: 餐饮场景 5-7 个核心实体 (店/菜/人/桌/账单/食材/客户) 已知, 比通用 MDM 少很多, 反而更易做透
2. **AI 原生**: 从架构层就是 AI-first, 不是给老 BI 加 AI 补丁 (后者是 Snowflake/Databricks 走的路, 包袱重)
3. **SMB 友好**: 不要求客户接 API, 不要求换 POS, 上传 Excel 就行. 入门成本 0.

## 3. 4 个 Sub-Project 总览

### Sub-Project A: 能力驱动渲染 (Capability-based Rendering)

**目标**: 客户上传任何 CSV 后, Dashboard / 模板 / KPI 卡片**只显示当前数据能算的内容**, 不显示 0 / 空 / 误导. 缺什么数据就友好提示客户补什么.

**工作量**: ~1 周 (5-7 天)

**核心改动**:
- 给所有 Dashboard 卡片 / 44 个 template / KPI 项 加 `requires: [field_list]` metadata
- 实现 `CapabilityCalculator(factory_id) → set[available_fields]` (聚合所有上传的 field_definitions)
- 渲染层 pre-filter: `requires.issubset(available)` 才渲染
- 增加 "解锁更多分析" CTA: 列出客户当前缺什么文件, 上传后能解锁什么

**为什么先做**: 立即有产品价值, 客户不再被空卡片误导, 也是后续 B/C/D 的依赖底座 (B/C/D 的输出最终都要通过 Capability gate 控制可见性)

**详细 spec**: `02-A-能力驱动渲染.md`

### Sub-Project B: 实体解析与形态路由 (Entity Resolution + Shape Router)

**目标**: 客户上传**任何形态**的文件, 系统:
1. 自动识别文件形态 (账单流水/商品汇总/评论/财务/库存/排班/...)
2. 路由到对应的 Silver 写入路径
3. 跨文件**用 AI 识别同一个店/菜/人**, 即使写法不同

**工作量**: ~2-3 周 (10-14 天)

**核心改动**:
- **Multi-Agent RAG 实体解析框架**:
  - `DeterministicAgent` (升级现有 alias_normalizer)
  - `EmbeddingAgent` (Qwen embedding + 余弦相似度)
  - `ContextualAgent` (店名+城市+区, 菜名+品类+店, 等结构化上下文 embedding)
  - `TransitiveAgent` (A=B, B=C ⇒ A=C 闭包)
  - `LLMArbitrator` (低置信度上 Qwen-Max)
- **Shape Detector (升级现有 domain_detector)**:
  - LLM-driven 文件形态识别 (账单流水/商品汇总/评论/财务/库存/排班/会员)
  - 返回置信度, 低置信度时弹窗确认
- **Shape Router**:
  - 基于 shape 路由到 5+ 种 Silver 写入路径 (扩展现有 backfill_silver.py)
  - 商品汇总路径: 写 `agg_product_*` 表, 跳过 fact_pos_item (没账单数据)
  - 评论路径: 写 `dim_review_summary` (新表)
  - 财务路径: 写 `fact_finance_voucher` (新表)
- **Admin UI**: 低置信度实体配对的人工裁决界面

**关键依赖**: A (template requires metadata 是 shape-aware 渲染的基础)

**详细 spec**: `03-B-实体解析与形态路由.md`

### Sub-Project C: 字段血统与继承 (Field Provenance + Inheritance Cascade)

**目标**: 多个文件可能给同一字段不同值时, 系统**自动选最优值**, 并对所有派生 KPI 标注**置信度 + 来源**, 让客户审计可追溯.

**工作量**: ~1-2 周 (7-10 天)

**核心改动**:
- **Cell-level Provenance Schema** (新表 `field_provenance`):
  - (factory_id, entity_type, entity_id, field_name) → [(source_upload_id, value, confidence, valid_from, valid_to, mapper_method)]
- **Conflict Resolution Rules**:
  - 优先级: 客户手动 > 官方 POS > 辅助文件 > 第三方平台 > AI 推断 > 行业默认
  - 时间窗口不重叠 → 各负责自己时段
  - 时间窗口重叠 → 取最新上传, 旧的标 superseded
  - 差异 > 30% → 弹窗让客户裁决
- **Inheritance Cascade Engine**:
  - 配方 (静态属性) → 所有时段销售 (动态记录) 通用
  - 账单流水有日期 → 同月商品汇总自动获日期窗口
  - 跨文件粒度升级 (店级 → 月级, 月级 → 日级)
- **Trust Indicator UI**: KPI 卡上显示数据来源 + 置信度 (如 "📊 客单价 ¥147 [来自账单流水, 100%]")

**关键依赖**: B (实体解析做了, 同一实体跨上传才能 join, 才有 provenance 可比较)

**详细 spec**: `04-C-字段血统与继承.md`

### Sub-Project D: 联邦查询引擎 (Federated Query Engine)

**目标**: 用户问任何业务问题, 系统**自动**拆解 → 跨多个 fact / agg 表 join → 返回结果. 模板编写者**不再写 SQL**, 只声明"我需要哪些字段, 怎么聚合".

**工作量**: ~1-2 周 (7-10 天)

**核心改动**:
- **Query Planner (LLM-augmented)**:
  - 输入: 用户问题 + 当前 factory 可用字段集合
  - 输出: 逻辑查询计划 (字段路由 + join 路径 + 聚合策略)
- **Logical → Physical SQL Generator**:
  - 自动选最优 fact/agg 表 (粗粒度 agg 优先, 缺时回退 fact)
  - Auto-join via entity_id (Sub-Project B 的产出)
  - 支持时间维度自动对齐 (日 → 月 → 季 → 年)
- **Template DSL 升级**:
  - 把现有 44 个 template 的 hardcoded SQL 改为声明式 DSL
  - 编译期生成 SQL, 运行期由 query planner 优化
- **Confidence Cascade**: 每个 join 边带 confidence (来自 B 的实体解析), 输出整体可信度

**关键依赖**: C (provenance 给 query planner 字段优先级 + 可信度信号)

**详细 spec**: `05-D-联邦查询引擎.md`

## 4. 依赖关系与工作流

```
        Bronze 层 (已有)
              ↓
        ┌─────────────┐
        │  上传形态    │
        │  Detector   │← B
        └──────┬──────┘
               ↓
   ┌───────────┼───────────┐
   ↓           ↓           ↓
账单流水    商品汇总    评论/财务/库存
   ↓           ↓           ↓
        Silver 写入路径
        ↓
        ┌─────────────────┐
        │ Multi-Agent RAG │← B
        │ Entity Resolver │
        └────────┬────────┘
                 ↓
        ┌─────────────────┐
        │ Field           │← C
        │ Provenance      │
        └────────┬────────┘
                 ↓
        ┌─────────────────┐
        │ Inheritance     │← C
        │ Cascade         │
        └────────┬────────┘
                 ↓
        ┌─────────────────┐
        │ Federated Query │← D
        │ Engine          │
        └────────┬────────┘
                 ↓
        ┌─────────────────┐
        │ Capability      │← A
        │ Renderer        │
        └────────┬────────┘
                 ↓
            Dashboard / 模板 / AI 问答
```

**严格依赖**: A 独立 → B 依赖 A → C 依赖 B → D 依赖 C.

**为何不能并行 4 个 sub-project**:
- B 的 entity_id 是 C/D 的 join key
- C 的 provenance 是 D 的优先级信号
- 4 个 sub-project 都修改重叠文件 (44 个 template / dim_* 表 / `materialized_analytics/` / Dashboard.vue)

**正确并行模式**:
- 每个 sub-project 内部用 subagent 并行 (FE + BE + 测试 + 文档同时跑)
- sub-project 之间串行

## 6. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| **LLM 实体解析准确率不达标 (< 90%)** | 跨文件 join 错误, KPI 失真 | (1) 先用 baseline (embedding+fuzzy) 跑, 准确率不达标再上 multi-agent. (2) 低置信度全部进 admin 队列. (3) 客户裁决一次后入 mapper_method='manual', 永久生效. |
| **多 Agent 编排复杂度爆炸** | 调试难, bug 难定位 | (1) 每 agent 独立单元测试. (2) Orchestrator 输出 trace log 可观测. (3) 加 feature flag, 单 agent 跑不通可降级到上一 agent. |
| **依赖链紧, B 卡住整个项目** | 进度风险 | (1) A 独立, 先上 prod 收第一波价值. (2) B 内部用 spike 验证 Multi-Agent 准确率, 1 周内确认走还是退到 baseline. |
| **现有 44 个 template 迁移到 D 的 DSL 工作量超预期** | D 阶段拖到 2-3 周 | (1) 不强制全迁, 新 template 用 DSL, 老的保留. (2) 高频 template 优先迁. |
| **客户 Excel 形态超预期 (10+ 种)** | Shape Detector 准确率下降 | (1) Detector 输出"未知"时进 admin 队列, 客户/内部标签后训练. (2) 加新形态成本: 1 个 detector rule + 1 个 Silver writer + 1 个 template 子集, 标准化流程 < 1 天/形态. |
| **Multi-Agent RAG LLM 成本超支** | 月度运营成本上涨 | (1) 99% 实体匹配靠便宜 agent (deterministic + embedding), LLM 只看灰色区. (2) 实体匹配结果缓存到 dim 表, 同上传内重复对比 0 cost. |

### 7.2 LLM 运营成本估算 (月度)

假设系统服务 100 个 factory tenant, 每个月新增 5 个上传, 每上传平均 1000 行:

| 调用 | 频率 | 单次 cost | 月度 |
|---|---|---|---|
| Shape Detector (LLM 看前 5 行) | 100 × 5 = 500 次 | ~¥0.05 (qwen-plus) | ¥25 |
| Entity Resolution (LLM 仅灰色区, 99% 走便宜 agent) | ~10K 次/月 | ~¥0.005 (qwen-plus) | ¥50 |
| Embedding (店/菜/人 名字) | ~50K 次/月 | ~¥0.0001 (text-embedding-v3) | ¥5 |
| Query Planner (用户问问题时) | ~100K 次/月 | ~¥0.01 (qwen-max) | ¥1000 |
| AI Insight (Dashboard 洞察) | 已有, 不变 | - | (现有) |
| **小计** | | | **~¥1080/月** (100 tenants) |

**单 tenant 月成本 ¥10.8**, 远低于客户单价 (假设 ¥500-2000/月). 经济性成立.

无新增. 所有改动在现有 Postgres + Python + Java 栈内完成.
