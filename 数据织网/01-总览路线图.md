## 1. 摘要

本文档定义 Cretas 餐饮 SaaS 升级为**多源数据融合 + AI 实体解析 + 联邦查询**架构 (业界 Data Fabric / MDM) 的路线图.

**目标**: 客户上传**任何格式**的餐饮业务文件, 系统自动识别 → 解析 → 融合 → 分析, 不依赖单一数据源, 不强制客户改变工作流.

**真实现状盘点** (经审计修正):
- **基础设施层 ~60% Production**: Bronze (smart_bi_*) / Silver (5 dim + 4 fact) / Gold (3 agg) / Multi-Tenant RLS / 44 分析模板 (`applies()` 自过滤) / 字段映射注册表 (`field_registry`)
- **Data Fabric 4 大能力本身 ~10-15%**: 仅 `applies()` 模板级过滤 + rule-based domain detector 部分覆盖. 实体解析 / 字段血统 / 联邦查询 / 能力驱动渲染 这 4 块**几乎从零开始**

**4 个 Sub-Project 工作量** (含 deploy/test/review/debug overhead):

| Sub-Project | 单工程师工作量 | 关键依赖 |
|---|---|---|
| A: 能力驱动渲染契约层 | 1.5-2 周 | 无 (可与 B 并行) |
| B: 实体解析 + 形态路由 | 3-5 周 | A 的契约 schema |
| C: 字段血统 + 继承 | 2-3 周 | B 的实体 ID |
| D: 联邦查询引擎 | 2-3 周 | C 的 provenance |
| **合计** | **8.5-13 周** (单工) | |
| **多人并行可压缩** | **6-9 周** | A 与 B 并行 + 内部 subagent |

**MVP 切分选项** (如果 8.5+ 周不能等):
- **MVP-A** (3-4 周): A 契约层 + B-baseline (仅 deterministic + embedding) + 2 个新形态 (商品汇总 + 评论)
- **完整版** (8.5-13 周): MVP-A + Multi-Agent 升级 + C + D

**LLM 月度成本** (默认档位 1 经济档):
- **100 tenants × ¥10.5/tenant = ¥1,050/月**
- 实现路径: 4 杠杆叠加 (模板缓存 80% 命中 + qwen-plus 默认 + Planner 触发率限 10% + 日预算 cap)
- 架构**同时支持档位 2 平衡档** (¥5,000/月, ¥50/tenant), 通过 config flag 切换, 无需重新架构

## 2. 战略背景

### 2.1 客户痛点

中小餐饮连锁 (10-200 门店) **数据碎片化**:
- 不同门店用不同 POS (历史并购 / 品牌差异)
- 总部 ERP / 供应链 / 人事是另一套
- 大众点评 / 美团 / 抖音外卖数据是平台导出
- 财务在金蝶 / 用友
- 各系统**字段不同 / 命名不同 / 粒度不同**

商家想看"昨天哪家店哪道菜亏钱了"这种简单问题, 现实要打开 6 个系统手工拼数据. 已有 BI 工具假设客户用单一 POS, 现实根本不成立.

### 2.2 行业现状 (调研于 2026-04-25)

| 厂商 | 强项 | 缺什么 (我们的机会) |
|---|---|---|
| **Snowflake Cortex Code** (2025-11 上线, 2026-04 升级) | "agentic enterprise", LLM 跨数据栈编排 | 通用产品, 餐饮场景需深度定制; 年费数十万美元, SMB 用不起 |
| **Databricks Unity Catalog** (2026-04 加 AI_parse_document) | 文档→表 AI 抽取已商业化 | 同上, 通用 + 贵 |
| **Salesforce Data Cloud** | Identity Resolution 商业化 | 专攻客户数据 (CDP), 不做餐饮业务实体 |
| **Atlan / Alation** | Data Catalog + Provenance | 只做元数据, 不做查询 + 分析 |
| **阿里 Dataphin** | MDM + 数据治理, 主打金融政府 | 年费 50万+, 餐饮 SMB 用不起 |
| **客如云 / 二维火 / 哗啦啦 / 美味不用等** | POS 主战场 | **数据分析弱, 多源融合几乎没有, AI 极少** |

**全球共同盲点**: 没有一家**真正解决"商家有 N 种格式碎片化数据"问题**. 大厂工具贵且通用, 小厂 SaaS 锁定单一 POS. 我们的位置在两者之间.

### 2.3 LLM 实体解析 SOTA

| 技术 | 准确率 | 成本 | 我们的策略 |
|---|---|---|---|
| Multi-Agent RAG (Preprints 2025-10) | 94.3% (姓名变体), -61% LLM 调用 | 中 | **二阶段升级**: 先 baseline, 不达标再加 |
| Embeddings + Fuzzy + Deterministic (主流) | 90-95% | 中 | **MVP baseline** |
| Probabilistic Record Linkage (Cambridge 2025) | 88-92% | 低 | 算法参考 |

**关键工程经验**: "Embedding **结构化上下文** (店名+城市+区+品牌) 而不是裸名字" 准确率提升 8-15%.

### 2.4 我们的战略定位

> **不抢 POS 主战场, 做"任何餐饮商家的多源数据融合 + AI 分析"层**

3 条防御:
1. **垂直深度**: 餐饮场景 5-7 个核心实体 (店/菜/人/桌/账单/食材/客户) 已知, 比通用 MDM 易做透
2. **AI 原生**: 架构层就是 AI-first, 不是给老 BI 加补丁
3. **SMB 友好**: 不要求接 API, 不要求换 POS, 上传 Excel 就行 (但客户仍需上传文件 + 培训内部 + 接受 AI 仲裁结果, 不是"零成本")

| 能力 | 当前状态 | 缺什么 | 完成度 |
|---|---|---|---|
| **A 能力驱动渲染** | template-level `applies()` 已用 | cell/card/KPI-level `requires:` metadata + CapabilityCalculator + 渲染 pre-filter + "解锁 CTA" | **~20%** |
| **B 实体解析** | exact-match UPSERT + 简繁归一化 | fuzzy / embedding / contextual / transitive / LLM arbitrate 全部未做 | **~5%** |
| **B 形态路由** | rule-based detector (RESTAURANT vs UNKNOWN) 存了**没用** | LLM-driven 形态识别 + 5+ 种 Silver 写入路径 + admin 裁决 UI | **~10%** |

**总和约 10-15%** (基础设施铺好了, 但 4 大功能本身需要从骨架往上长肉).

## 4. 4 个 Sub-Project 详细范围

### 4.1 Sub-Project A: 能力驱动渲染契约层 (Capability Contract Layer)

**重要重定位 (v1.1)**: A 是**契约层**, 不是下游消费层. A 提供 metadata schema + Calculator API, B/C/D 在做完功能后填这个契约. 因此 A 可以与 B 并行启动, 不阻塞.

**目标**:
1. 定义全系统统一的 `requires: [field_list]` 元数据格式
2. 提供 `CapabilityCalculator(factory_id) → set[available_fields]` 接口
3. 渲染层 pre-filter: `requires.issubset(available)` 才渲染
4. 缺数据时显"解锁更多分析" CTA, 不显空卡片

**工作量**: 1.5-2 周 (含 overhead)

**核心交付**:
- 契约 schema 文档 (`docs/data-fabric/capability-contract.md`)
- 给现有 Dashboard 卡片 / 44 个 template / KPI 项 加 `requires` 元数据 (~80 处)
- `CapabilityCalculator` Python 类 + Java 等价
- 渲染层 pre-filter (Vue 组件 wrap + Java endpoint guard)
- "解锁 CTA" Vue 组件 (现有 el-empty 升级)
- E2E 测试 + admin 审计页

**关键设计**: A 的 metadata schema **必须**先于 B/C/D 完成 1 周, 这样后者可以在做新功能时直接填契约, 不需要回头补.

**详细 spec**: `02-A-能力驱动渲染.md`

### 4.2 Sub-Project B: 实体解析 + 形态路由

**v1.1 修订**: Multi-Agent RAG 改为**渐进策略**, 不是 day 1 就 5 个 agent.

**目标**:
1. 自动识别上传文件形态 (账单流水 / 商品汇总 / 评论 / 财务 / 库存 / 排班 / 会员 等 7+ 种)
2. 路由到对应 Silver 写入路径 (扩展现有 `backfill_silver.py` + 新建 4-5 种 writer)
3. 跨文件**用 AI 识别同一个店/菜/人**, 即使写法不同

**Multi-Agent 渐进策略**:

```
阶段 B1 (MVP, 1.5-2 周): baseline 2-agent
  ├── DeterministicAgent (升级 alias_normalizer.py)
  └── EmbeddingAgent (Qwen text-embedding-v3 + 余弦)

跑标记数据集 (500 对店名 / 500 对菜名 / 200 对人名)
  ↓
准确率 ≥ 90%? → ✅ ship baseline, 不再加
准确率 < 90%? → 进入 B2
准确率 < 75%? → 急停, 重新设计 baseline

阶段 B2 (升级, 1-1.5 周): 加 ContextualAgent + LLMArbitrator
  ├── ContextualAgent (店名+城市+区, 菜名+品类+店 上下文 embedding)
  ├── TransitiveAgent (A=B, B=C → A=C 闭包)
  └── LLMArbitrator (低置信度上 qwen-plus, 不是 qwen-max)

再跑标记集, 95% 才 ship
```

**工作量**:
- B1 baseline: 1.5-2 周
- 评估 + 决策: 0.5 周
- B2 升级 (条件触发): 1-1.5 周
- Shape Detector + Router: 1.5-2 周 (并行 B1)
- **小计 3-5 周** (取决于 baseline 是否达标)

**核心交付**:
- `EntityResolutionOrchestrator` (B1 仅 2 agent, B2 扩 5 agent)
- 标记数据集 (500+500+200 对)
- `ShapeDetector` (LLM-driven, qwen-plus, 低置信度入 admin 队列)
- `ShapeRouter` (路由到 Silver writer)
- 5 种新 Silver writer:
  - `ProductSummaryWriter` (商品汇总, 写新 `agg_product_period` 表)
  - `ReviewWriter` (评论, 写新 `dim_review_summary` 表)
  - `FinanceWriter` (财务凭证, 写新 `fact_finance_voucher` 表)
  - `InventoryWriter` (库存盘点, 写新 `fact_inventory_snapshot` 表)
  - `ScheduleWriter` (排班, 写新 `fact_staff_schedule` 表)
- Admin 实体配对裁决 UI (复用 `dim_discount.parsed_ok` 模式)

**关键依赖**:
- A 的 `requires` 契约 (新表的字段映射要填契约)
- 现有 `field_registry` (扩展 mapper_method = 'embedding'/'multi_agent')

**详细 spec**: `03-B-实体解析与形态路由.md`

### 4.3 Sub-Project C: 字段血统 + 继承

**目标**:
1. 多个文件可能给同一字段不同值时, 系统自动选最优值
2. 所有派生 KPI 标注 **置信度 + 来源**, 客户可审计
3. 配方 → 销售 → 毛利 这种"长期属性 + 动态记录" 的继承自动化

**工作量**: 2-3 周 (含 overhead)

**核心交付**:
- **`field_provenance` 表** (新 schema):
  ```sql
  CREATE TABLE field_provenance (
    id BIGSERIAL PRIMARY KEY,
    factory_id VARCHAR(50) NOT NULL,
    entity_type VARCHAR(50) NOT NULL,       -- 'store' / 'product' / 'staff' / 'bill' / ...
    entity_id BIGINT NOT NULL,
    field_name VARCHAR(100) NOT NULL,
    field_value JSONB NOT NULL,             -- polymorphic
    source_upload_id BIGINT,
    source_type VARCHAR(50),
    confidence NUMERIC(3,2),                -- 0.00-1.00
    valid_from DATE,
    valid_to DATE,
    mapper_method VARCHAR(20),              -- 'manual' / 'rule' / 'embedding' / 'llm'
    superseded_by_id BIGINT REFERENCES field_provenance(id),
    created_at TIMESTAMP DEFAULT NOW()
  );
  -- + factory_id RLS FORCE
  -- + index on (factory_id, entity_type, entity_id, field_name, valid_from)
  ```
- **冲突解决规则引擎**:
  - 优先级: 客户手动 > 官方 POS > 辅助文件 > 第三方平台 > AI 推断 > 行业默认
  - 时间窗不重叠 → 各负责自己时段
  - 时间窗重叠 → 取最新, 旧的 superseded
  - 差异 > 30% → 弹窗让客户裁决
- **继承 cascade engine**:
  - 静态属性 (配方/标签) → 所有时段动态记录
  - 时间继承 (账单流水有日期 → 同月商品汇总获日期窗)
  - 粒度升级 (店级 → 月级 → 日级)
- **Trust Indicator UI**: KPI 卡显示 "📊 客单价 ¥147 [来自账单流水, 100%]"

**关键依赖**: B 的实体解析 (entity_id 必须稳定, 跨上传一致)

**详细 spec**: `04-C-字段血统与继承.md`

### 4.4 Sub-Project D: 联邦查询引擎

**目标**: 用户问任何业务问题, 系统**自动**拆解 → 跨多个 fact / agg 表 join → 返回结果. 模板编写者不再写 SQL.

**工作量**: 2-3 周 (含 overhead)

**核心交付**:
- **Query Planner** (LLM-augmented, 默认 qwen-plus):
  - 输入: 用户问题 + factory 可用字段集合 (来自 A 的 Calculator)
  - 输出: 逻辑查询计划 (字段路由 + join 路径 + 聚合策略)
  - **触发率限制**: 仅在模板没匹配 + 自然语言问答时启用 (默认档位 1 ~10% 触发)
- **Logical → Physical SQL Generator**:
  - 自动选最优 fact/agg 表 (粗 agg 优先, 缺时回退 fact)
  - Auto-join via entity_id (B 产出)
  - 时间维度自动对齐 (日 → 月 → 季)
- **Template DSL**:
  - 高频模板迁移到声明式 DSL (低频保留 SQL)
  - 编译期生成 SQL, 运行期 query planner 优化
- **Confidence Cascade**:
  - 每个 join 边带 confidence (来自 C 的 provenance)
  - 输出整体可信度

**关键依赖**: C 的 provenance (字段优先级 + join confidence)

**详细 spec**: `05-D-联邦查询引擎.md`

## 5. Sub-Project 边界 Gap 处理 (新增, v1.1)

**问题**: B 在 M2 完成时引入 4 种新表 (`agg_product_period` / `dim_review_summary` / `fact_finance_voucher` / `fact_inventory_snapshot`), 但 D 还没启动, **客户上传评论后 Dashboard 啥都看不见** (表里有数据, 模板查不出来).

**解决**: A 的 capability gate 扛住. B 上完后:

1. **新表的最小可用模板**先做 (每种形态 1-2 个最简单的看板, 不依赖联邦查询)
   - 商品汇总 → "商品销售 Top 10" (单表查询, agg_product_period)
   - 评论 → "评分趋势 + Top 关键词" (单表 dim_review_summary)
   - 财务 → "月度收支" (单表 fact_finance_voucher)
   - 库存 → "库存预警" (单表 fact_inventory_snapshot)
2. 这些模板填 `requires` 契约 → A 的 capability gate 在客户传对应文件时**自动解锁**
3. **D 完成后**, 跨文件融合分析 (例如"评分高但卖差的菜") 才出现, 不影响 B 单独的产品价值

**工作量影响**: 每种形态多 1-2 个简单模板, ~0.5 天/形态 × 4 = +2 天 (已含在 B 的 3-5 周内).

## 7. 里程碑与 Smoke Verification Gates (v1.1 新增)

### M1: A 完成 (Week 2)

| **9** | **LLM provider (DashScope/Qwen) 宕机** | **Multi-Agent + Query Planner 全挂, 客户问答 timeout** | (1) 复用 Apr 25 commit 的 `call_chain` migration 模式 (AIQuery/Agent/InsightGen 已有 fallback). (2) Embedding 失败时降级到 fuzzy matching (deterministic + Levenshtein), 准确率掉但不挂. (3) Planner 失败时降级到模板匹配, 提示"复杂查询暂不可用". |

## 9. LLM 成本模型 (v1.1 完整版)

### 9.1 真实定价 (qwen-max vs qwen-plus, 2026-04 公开)

| 模型 | 输入 ¥/1K tokens | 输出 ¥/1K tokens | 适用 |
|---|---|---|---|
| qwen-max | ¥0.04 | ¥0.12 | 复杂查询规划, 模糊实体仲裁 |
| qwen-plus | ¥0.008 | ¥0.024 | 默认 LLM, 形态识别, 简单实体 |
| qwen-turbo | ¥0.0006 | ¥0.0006 | 单字段映射 (备选) |
| text-embedding-v3 | ¥0.0007/1K | - | 名字向量化 |

### 9.2 4 杠杆叠加 (默认档位 1)

```
用户 100K 问题/月 (100 tenants × ~33/天)
  ↓
[杠杆 1] 模板缓存命中? (默认 80%)
  ├─ 是 (80K) → ¥0
  └─ 否 (20K)
      ↓
[杠杆 2] 是 NL 问答 / 模板没匹配? (50%)
  ├─ 否 (10K, 是结构化查询) → 直接走 SQL ¥0
  └─ 是 (10K) → Query Planner
      ↓
[杠杆 3] 复杂度高 (跨 5+ 表)? (20%)
  ├─ 否 (8K, 用 qwen-plus) → ¥0.04/call × 8K = ¥320
  └─ 是 (2K, 用 qwen-max) → ¥0.30/call × 2K = ¥600
[杠杆 4] 单 tenant 日 cap (复用 agent_budget_daily) → 防失控
```

| 路径 | 月调用 | 单次 | 月成本 |
|---|---|---|---|
| 模板缓存命中 | 80K | ¥0 | ¥0 |
| 直接 SQL | 10K | ¥0 | ¥0 |
| Query Planner (qwen-plus) | 8K | ¥0.04 | ¥320 |
| Query Planner (qwen-max) | 2K | ¥0.30 | ¥600 |
| Entity LLM 仲裁 (灰色 1%) | 10K | ¥0.012 | ¥120 |
| Shape Detector | 500 | ¥0.018 | ¥9 |
| Embedding (店/菜/人) | 50K | ¥0.00004 | ¥2 |
| **合计** | | | **¥1,051/月** (100 tenants) |

**单 tenant 月 ¥10.5**, 客单价 ¥500-2000, **LLM 占比 0.5-2%**, 健康.

## 10. MVP 切分 (v1.1 新增)

如果 8.5-13 周不能等, 推荐 **MVP-A (3-4 周)**:

| 阶段 | 内容 | 工作量 | 业务价值 |
|---|---|---|---|
| MVP-A | A 契约层 + B-baseline (仅 deterministic + embedding) + 2 形态 (商品汇总 + 评论) + 4 个最小模板 | **3-4 周** | 任何 CSV 上传不再误导, 商品汇总 + 评论可分析, 实体跨上传识别 |
| 后续 1 | B-Multi-Agent 升级 (条件触发) + 3 形态 (财务 + 库存 + 排班) | +2-3 周 | 更高准确率 + 更多形态 |
| 后续 2 | C 字段血统 + 继承 | +2-3 周 | 多源融合自动选最优值 |
| 后续 3 | D 联邦查询 | +2-3 周 | NL 问答 + 跨表 auto-join |

**推荐路径**: 先 MVP-A 3-4 周上 prod 收第一波价值 → 看客户反馈 → 决定后续 1/2/3 优先级.

**不推荐**: 一气呵成跑完整 13 周再上, 风险大反馈慢.
