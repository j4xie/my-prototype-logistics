## 1. 摘要

本文档定义 Cretas 餐饮 SaaS 升级为**多源数据融合 + AI 实体解析 + 联邦查询**架构 (业界 Data Fabric / MDM) 的路线图.

**目标**: 客户上传**任何格式**的餐饮业务文件, 系统自动识别 → 解析 → 融合 → 分析, 不依赖单一数据源, 不强制客户改变工作流.

**真实现状盘点** (经审计修正):
- **基础设施层 ~60% Production**: Bronze (smart_bi_*) / Silver (5 dim + 4 fact) / Gold (3 agg) / Multi-Tenant RLS / 44 分析模板 (`applies()` 自过滤) / 字段映射注册表 (`field_registry`)
- **Data Fabric 4 大能力本身 ~10-15%**: 仅 `applies()` 模板级过滤 + rule-based domain detector 部分覆盖. 实体解析 / 字段血统 / 联邦查询 / 能力驱动渲染 这 4 块**几乎从零开始**

**4 个 Sub-Project 工作量** (含 deploy/test/review/debug overhead, v1.2 修正):

| Sub-Project | 单工程师工作量 | 关键依赖 |
|---|---|---|
| A: 能力驱动渲染契约层 | 2-2.5 周 (02-A spec v1.2 校准) | 无 (可与 B 并行) |
| B: 实体解析 + 形态路由 + Sheet Merger + 4 MVP 模板 + 标注 + 并发 | **5.5-8 周** (v1.2 加 Sheet Merger 0.5-1 周) | A 的契约 schema |
| C: 字段血统 + 继承 + §11.5 回填 | 2.5-3.5 周 | B 的实体 ID |
| D: 联邦查询引擎 | 2-3 周 | C 的 provenance |
| **合计** | **12-17 周** (单工, v1.2 微增) | |
| **多人并行可压缩** | **8-12 周** | A 与 B 并行 + 内部 subagent |

**MVP 切分选项** (如果 12+ 周不能等):
- **MVP-A** (5-6 周, v1.2 修正): A 契约层 + B-baseline (仅 deterministic + embedding) + 标注 SOP + 并发 + 2 个新形态 (商品汇总 + 评论) × 1 MVP 模板
- **完整版** (12-15.5 周): MVP-A + Multi-Agent 升级 + 2 形态 (财务 + 库存) + C + D

**LLM 月度成本** (默认档位 1 经济档, v1.2 重算 — B S-NEW-6 影响, 含 agent_insights):
- **P50: 100 tenants × ¥96/tenant = ¥9,631/月** (含 Week 5 agent_insights 现有 prod 用量, 不能砍)
- **P90: ¥35,000/月** (30% cache + 80% Planner + 80% agent_insights)
- 默认档位 1 预算 cap **¥10,000/月** (P50 + ~5% 缓冲)
- 4 杠杆: 模板缓存 + qwen-plus 默认 + Planner 触发率限 + 日预算 cap (复用 `agent_budget_daily`)
- 架构**同时支持档位 2 平衡档** (¥18,000/月, ¥180/tenant), 通过 config flag 切换
- ⚠️ **agent_insights 是月成本主导项** (¥7,200 of ¥9,631 P50). 真要降本只能砍 agent_insights 触发率, 但会影响 Week 5 现有体验

## 2. 战略背景

### 2.1 客户痛点

中小餐饮连锁 (10-200 门店) **数据碎片化**:
- 不同门店用不同 POS (历史并购 / 品牌差异)
- 总部 ERP / 供应链 / 人事是另一套
- 大众点评 / 美团 / 抖音外卖数据是平台导出
- 财务在金蝶 / 用友
- 各系统**字段不同 / 命名不同 / 粒度不同**

商家想看"昨天哪家店哪道菜亏钱了"这种简单问题, 现实要打开 6 个系统手工拼数据. 已有 BI 工具假设客户用单一 POS, 现实根本不成立.

### 2.2 行业现状 (调研于 2026-04-25)

| 厂商 | 强项 | 缺什么 (我们的机会) |
|---|---|---|
| **Snowflake Cortex Code** (2025-11 上线, 2026-04 升级) | "agentic enterprise", LLM 跨数据栈编排 | 通用产品, 餐饮场景需深度定制; 年费数十万美元, SMB 用不起 |
| **Databricks Unity Catalog** (2026-04 加 AI_parse_document) | 文档→表 AI 抽取已商业化 | 同上, 通用 + 贵 |
| **Salesforce Data Cloud** | Identity Resolution 商业化 | 专攻客户数据 (CDP), 不做餐饮业务实体 |
| **Atlan / Alation** | Data Catalog + Provenance | 只做元数据, 不做查询 + 分析 |
| **阿里 Dataphin** | MDM + 数据治理, 主打金融政府 | 年费 50万+, 餐饮 SMB 用不起 |
| **客如云 / 二维火 / 哗啦啦 / 美味不用等** | POS 主战场 | **数据分析弱, 多源融合几乎没有, AI 极少** |

**全球共同盲点**: 没有一家**真正解决"商家有 N 种格式碎片化数据"问题**. 大厂工具贵且通用, 小厂 SaaS 锁定单一 POS. 我们的位置在两者之间.

### 2.3 LLM 实体解析 SOTA

| 技术 | 准确率 | 成本 | 我们的策略 |
|---|---|---|---|
| Multi-Agent RAG (Preprints 2025-10) | 94.3% (姓名变体), -61% LLM 调用 | 中 | **二阶段升级**: 先 baseline, 不达标再加 |
| Embeddings + Fuzzy + Deterministic (主流) | 90-95% | 中 | **MVP baseline** |
| Probabilistic Record Linkage (Cambridge 2025) | 88-92% | 低 | 算法参考 |

**关键工程经验**: "Embedding **结构化上下文** (店名+城市+区+品牌) 而不是裸名字" 准确率提升 8-15%.

### 2.4 我们的战略定位

> **不抢 POS 主战场, 做"任何餐饮商家的多源数据融合 + AI 分析"层**

3 条防御:
1. **垂直深度**: 餐饮场景 5-7 个核心实体 (店/菜/人/桌/账单/食材/客户) 已知, 比通用 MDM 易做透
2. **AI 原生**: 架构层就是 AI-first, 不是给老 BI 加补丁
3. **SMB 友好**: 不要求接 API, 不要求换 POS, 上传 Excel 就行 (但客户仍需上传文件 + 培训内部 + 接受 AI 仲裁结果, 不是"零成本")

## 4. 4 个 Sub-Project 详细范围

### 4.1 Sub-Project A: 能力驱动渲染契约层 (Capability Contract Layer)

**重要重定位 (v1.1)**: A 是**契约层**, 不是下游消费层. A 提供 metadata schema + Calculator API, B/C/D 在做完功能后填这个契约. 因此 A 可以与 B 并行启动, 不阻塞.

**目标**:
1. 定义全系统统一的 `requires: [field_list]` 元数据格式
2. 提供 `CapabilityCalculator(factory_id) → set[available_fields]` 接口
3. 渲染层 pre-filter: `requires.issubset(available)` 才渲染
4. 缺数据时显"解锁更多分析" CTA, 不显空卡片

**工作量**: 1.5-2 周 (含 overhead)

**核心交付**:
- 契约 schema 文档 (`docs/data-fabric/capability-contract.md`)
- 给现有 Dashboard 卡片 / 44 个 template / KPI 项 加 `requires` 元数据 (~80 处)
- `CapabilityCalculator` Python 类 + Java 等价
- 渲染层 pre-filter (Vue 组件 wrap + Java endpoint guard)
- "解锁 CTA" Vue 组件 (现有 el-empty 升级)
- E2E 测试 + admin 审计页

**`requires:` Schema 格式** (v1.2 新增, 来自 NM-1):

权威来源 = `backfill_silver.py` 的 `_ALIAS_TO_ATTR` 字典 (12 个 canonical 字段, snake_case English):
`store_name`, `source_bill_no`, `date`, `staff_name`, `gross_amount`, `discount_amount`, `net_amount`, `actual_receive`, `customer_count`, `table_no`, `order_type`, `channel_origin`, `combo_string`. 加上将来 B 引入的: `product_name`, `qty`, `unit_price`, `review_text`, `rating`, `voucher_code`, etc.

```yaml
# 例子: 一个 Dashboard KPI 卡的 metadata
- card_id: avg_bill_value
  display: 客单价
  requires:
    - store_name        # canonical English, 不是 中文 "门店名称"
    - source_bill_no    # 决定卡片是否能算 (无账单号即隐藏)
    - net_amount
  computes_when: ALL_PRESENT
  description: 净销售额 / 账单数, 隐藏当任一字段缺失
```

**Calculator 解析逻辑**:

```python
def get_factory_capabilities(factory_id) -> set[str]:
    """聚合该 factory 所有 upload 的 field_definitions, 返回 canonical 字段集合"""
    raw_columns = scan_all_uploads(factory_id)  # ['门店名称', '账单号', '商品信息', ...]
    canonical_set = set()
    for raw in raw_columns:
        canonical = _ALIAS_TO_ATTR.get(raw)       # 中文 → English
        if canonical:
            canonical_set.add(canonical)
    return canonical_set  # {'store_name', 'source_bill_no', 'date', 'combo_string'}

def can_render(card_requires: list[str], available: set[str]) -> bool:
    return set(card_requires).issubset(available)
```

**为什么用 canonical English 而非中文**:
- ✅ 与 Silver `CanonicalRow` 一致 (同名字段 join 自然)
- ✅ 与 `field_registry.canonical_field` 一致 (B 完成后可直接查询)
- ✅ 多 POS 系统兼容 (qhj 用 "营业日期", xmx 用 "交易日期", 都映射 `date`)
- ⚠️ 但现有模板 `applies()` 还在用中文列名 (如 `dish_sales_top_n.applies()` 检查 `商品信息`). 解决: A 提供 `_ALIAS_TO_ATTR` 双向 lookup, applies() 内部继续用中文, capability gate 用 canonical, 互不影响

**关键设计**: A 的 metadata schema **必须**先于 B/C/D 完成 1 周, 这样后者可以在做新功能时直接填契约, 不需要回头补.

**详细 spec**: `02-A-能力驱动渲染.md`

#### 4.2.2 并发上传事务模型 (v1.2 新增, NS-4)

**问题**: 同一 factory 两个用户同时上传冲突 POS 文件, Entity Resolver 跑到一半 race condition → dim_store 重复行.

**当前代码现实** (调研发现):
- `excel_async.py`: FastAPI BackgroundTasks 单进程, **无 per-factory 串行化**
- `hooks.py _trigger_materialization`: fire-and-forget, **无 lock**
- `dim_resolver.py`: UPSERT 用 `INSERT ... ON CONFLICT DO UPDATE`, **行级原子安全** (Postgres 串行化)
- BUT: `dim_resolver.py` 第 121 行 in-memory cache **不线程安全** (注释明确)
- 完全无 `pg_advisory_xact_lock` 模式

**真实 race window** (不是 dim_* 写入, 而是 entity resolution 的"该用现有 ID 还是新建"判断):

```
T1: Upload A → resolver 查 "唏嘛香金虹桥店" → 找到 store_id=42
T1: Upload A → 用 42 写入 fact_pos_*
T2: Upload B → resolver 查 "金虹桥唏嘛香店" (变体) 
T2: → embedding 匹配到 42, 0.87 → ship 决策 "用 42"
T2: BUT 同时 Upload C 也在跑 → resolver 缓存还没更新 → 决策"新建 store_id=43"
T3: 现在 dim_store 有 42 和 43 两条**实际同一家店**的记录
```

**解决方案** (3 层防御):

```python
# Layer 1: per-factory advisory lock 包裹整个 entity resolution 阶段
async def resolve_entities(factory_id: str, upload_id: int):
    factory_lock_key = hash(factory_id) % (2**31)  # int4 范围
    async with pool.acquire() as conn:
        async with conn.transaction():
            # 同 factory 的 entity resolution 串行, 不同 factory 并行
            await conn.execute("SELECT pg_advisory_xact_lock($1)", factory_lock_key)
            await _resolve_inner(conn, upload_id)

# Layer 2: asyncio.Lock per factory (Python 进程内)  
_factory_locks: dict[str, asyncio.Lock] = defaultdict(asyncio.Lock)
async def trigger_materialization(factory_id, upload_id):
    async with _factory_locks[factory_id]:
        await _trigger_materialization(upload_id)

# Layer 3: dim_resolver in-memory cache 失效
# 每次 entity resolution 完成后, 清掉 self._cache (避免下一 upload 用旧映射)
```

**工作量**: 0.3-0.5 周 (1.5-2.5 天) — schema 加索引 + 上述 3 层包装 + 并发回归测试.

**详细 spec**: `03-B-实体解析与形态路由.md`

### 4.3 Sub-Project C: 字段血统 + 继承

**目标**:
1. 多个文件可能给同一字段不同值时, 系统自动选最优值
2. 所有派生 KPI 标注 **置信度 + 来源**, 客户可审计
3. 配方 → 销售 → 毛利 这种"长期属性 + 动态记录" 的继承自动化

**工作量**: 2-3 周 (含 overhead)

**核心交付**:
- **`field_provenance` 表** (新 schema):
  ```sql
  CREATE TABLE field_provenance (
    id BIGSERIAL PRIMARY KEY,
    factory_id VARCHAR(50) NOT NULL,
    entity_type VARCHAR(50) NOT NULL,       -- 'store' / 'product' / 'staff' / 'bill' / ...
    entity_id BIGINT NOT NULL,
    field_name VARCHAR(100) NOT NULL,
    field_value JSONB NOT NULL,             -- polymorphic
    source_upload_id BIGINT,
    source_type VARCHAR(50),
    confidence NUMERIC(3,2),                -- 0.00-1.00
    valid_from DATE,
    valid_to DATE,
    mapper_method VARCHAR(20),              -- 'manual' / 'rule' / 'embedding' / 'llm'
    superseded_by_id BIGINT REFERENCES field_provenance(id),
    created_at TIMESTAMP DEFAULT NOW()
  );
  -- + factory_id RLS FORCE
  -- + index on (factory_id, entity_type, entity_id, field_name, valid_from)
  ```
- **冲突解决规则引擎**:
  - 优先级: 客户手动 > 官方 POS > 辅助文件 > 第三方平台 > AI 推断 > 行业默认
  - 时间窗不重叠 → 各负责自己时段
  - 时间窗重叠 → 取最新, 旧的 superseded
  - 差异 > 30% → 弹窗让客户裁决
- **继承 cascade engine**:
  - 静态属性 (配方/标签) → 所有时段动态记录
  - 时间继承 (账单流水有日期 → 同月商品汇总获日期窗)
  - 粒度升级 (店级 → 月级 → 日级)
- **Trust Indicator UI**: KPI 卡显示 "📊 客单价 ¥147 [来自账单流水, 100%]"

**关键依赖**: B 的实体解析 (entity_id 必须稳定, 跨上传一致)

**详细 spec**: `04-C-字段血统与继承.md`

### 4.4 Sub-Project D: 联邦查询引擎

**目标**: 用户问任何业务问题, 系统**自动**拆解 → 跨多个 fact / agg 表 join → 返回结果. 模板编写者不再写 SQL.

**工作量**: 2-3 周 (含 overhead)

**核心交付**:
- **Query Planner** (LLM-augmented, 默认 qwen-plus):
  - 输入: 用户问题 + factory 可用字段集合 (来自 A 的 Calculator)
  - 输出: 逻辑查询计划 (字段路由 + join 路径 + 聚合策略)
  - **触发率限制**: 仅在模板没匹配 + 自然语言问答时启用 (默认档位 1 ~10% 触发)
- **Logical → Physical SQL Generator**:
  - 自动选最优 fact/agg 表 (粗 agg 优先, 缺时回退 fact)
  - Auto-join via entity_id (B 产出)
  - 时间维度自动对齐 (日 → 月 → 季)
- **Template DSL**:
  - 高频模板迁移到声明式 DSL (低频保留 SQL)
  - 编译期生成 SQL, 运行期 query planner 优化
- **Confidence Cascade**:
  - 每个 join 边带 confidence (来自 C 的 provenance)
  - 输出整体可信度

**关键依赖**: C 的 provenance (字段优先级 + join confidence)

**详细 spec**: `05-D-联邦查询引擎.md`

## 11.5 现有数据回填策略 (v1.2 新增, NS-5)

**问题**: C 引入 `field_provenance` 表, 现有 12 factories 已有数据 (1.31M `fact_pos_item` 行) 没有 provenance 记录, M3 上线后这些 KPI 的 Trust UI 全是空白.

**真实规模 (查 prod pg_stat_user_tables 2026-04-25)**:

| 表 | 行数 | 影响 |
|---|---|---|
| `fact_pos_transaction` | 297,436 | 每行需 1-3 条 provenance (gross/discount/net) |
| `fact_pos_item` | 1,310,246 | 每行需 1-2 条 provenance (qty/amount) |
| `dim_product` | 2,703 | 每行 1 条 provenance (name 来源) |
| `dim_store` | 149 | 同上 |
| **预估 provenance 行总数** | **~3-4M** | 单表 schema migration 不能一次性完成 |

**回填策略**:

```
Phase 1 — Schema migration (M3 day 1):
  - 创建 field_provenance 表 + RLS + 索引
  - 默认空, 不影响现有读路径

Phase 2 — Backfill 现有数据 (M3 day 2-7, 后台批量):
  - 优先级: dim_* (小表) → fact_pos_transaction → fact_pos_item
  - Batch size: 5,000 行/批, 每批后 sleep 200ms 避免拖慢 prod
  - 默认值: 
    confidence = 0.5  (legacy, 中等置信度)
    mapper_method = 'legacy_backfill'
    valid_from = upload.created_at (从 source upload 推断)
    valid_to = NULL (持续有效)
  - 用 SKIP LOCKED 避免阻塞写入
  - 预估时间: 1.31M 行 / 5K batch / 200ms = 4.4 天后台跑完

Phase 3 — 双写过渡期 (M3 day 8 起):
  - 新写入同时填 fact_pos_* 和 field_provenance
  - 老 reader 仍读 fact_pos_*
  - 新 reader (Trust UI) 读 field_provenance
  - 持续 2 周观察一致性

Phase 4 — Cutover (M3 day 22+):
  - field_provenance 成为权威源 for Trust UI
  - 老 reader 路径保留 (兼容性)
```

**风险控制**:
- Test 环境 (cretas_db, ~10K 行) 先跑 1 整轮验证脚本
- Prod 跑前先 `pg_dump` 备份 fact_pos_* (~600MB 估)
- Rollback 计划: drop field_provenance 表 + 删迁移记录, 不影响现有数据
- 监控: 复制延迟 (`pg_stat_replication`) + active connections + lock waits

**工作量**: 1 周 (含验证 + prod 跑通) — **已含在 C 的 2.5-3.5 周内**.
