(Apr 24 2026 — 加入 Rule 15-17: wire payload 审计 / 独立 reviewer 同模式扫荡 / 入口点矩阵

在开始执行本次任何测试任务之前, 以及执行过程中的每一步, 严格遵守以下通用准则.
不管用户让我测什么功能/模块/流程, 都按这套标准来.


第一步: 先核对 — 确认"测试"是真端到端, 不是独立 smoke

在动手之前 + 执行完成后, 诚实对照下面 8 条逐项自查:

1. 数据来源: 是用测试新建的数据, 还是拿 seed 旧数据?
   - 用新建 → 有可能真端到端
   - 拿 seed → 只能算独立 smoke 验证, 不能报告为 deep

2. 跨模块联动: 数据是否从模块 A 真实流转到模块 B?
   - 如 SO approve 后采购/生产/发货单是否回写 → 真端到端
   - 各模块点点自己的按钮但数据不关联 → 独立验证

3. 跨模块回写校验: 操作后是否回到源头页面 (如 SO 详情页) 验证关联 Tab 显示新建记录?
   - Tab "采购订单"/"发货记录"/"开票申请"/"关联采购" 看到刚建的关联单 → 真端到端
   - 只在单模块里看到 toast 成功 → 独立验证

4. 操作方式: 是真 Playwright Locator API 还是 DOM 快捷方式?
   - browser_click with ref= → 真 mouse event (可信)
   - page.evaluate('...click()') / JS DOM → 不算真实用户操作
   - form.fill() 直接改值不触发 input event → 可疑

5. Console 监控: 每步后有没有调 browser_console_messages level=error?
   - 有 + 0 红色 error → 可信
   - 没监控 → 不能断言"无 error", 要补

6. Network 监控: 每步后有没有调 browser_network_requests 验证?
   - API status 200 + URL 正确 (无双前缀 /api/mobile/api/mobile/) → 可信
   - 没查 → 不能断言 API 健康

7. UI 文案核对 — 用户真实看到了什么?
   - 成功路径: 点击后 toast "XX 成功" 是否出现? 文案是否准确?
   - 错误路径 (关键): 触发 4xx/5xx 后, .el-message / .el-notification / dialog 文案 =
     后端 response.data.message 精确, 还是 fallback "操作失败/请检查网络"?
   - 工具: 必须用 MutationObserver 抓, 不能用 querySelectorAll (toast 3s fade,
     race condition 会拿到空数组 → 误判):

     // 操作前安装 observer
     browser_evaluate(() => {
       window.__toastLog = [];
       new MutationObserver(muts => muts.forEach(m => m.addedNodes.forEach(n => {
         if (n.nodeType === 1 && typeof n.className === 'string' &&
             (n.className.includes('el-message') || n.className.includes('el-notification')))
           window.__toastLog.push({ time: Date.now(), cls: n.className, text: n.textContent.trim() });
       }))).observe(document.body, { childList: true, subtree: true });
     });
     // 操作 + 等待
     // 读 log
     browser_evaluate(() => window.__toastLog);

   - 判定:
     * 文案 = 后端 message → 可信
     * 文案 = fallback ("xxx 失败") → Bug UX (吞 message)
     * log 空 → Bug silent failure
   - 为什么重要:
     * console "Failed to load resource: 400" 是浏览器原生字符串, 不代表用户看到了原因
     * querySelectorAll 直接抓 DOM 在 toast fade 后拿到空, 误判成"吞 message"
     * "API 400" + "console 有红色" = 系统层检测到错, 不等于用户体验正常

8. 流程依赖错误 UX 检查 — 错误体验和成功体验同等严格
   - 流程依赖错误定义: 用户点 B 失败是因为 A 未完成 (如"批次未分配不能发货"/
     "未审核不能开票"/"库存不足不能出库"/"未提交不能审批")
   - 三要素检查:
     a) 具体: toast 文案说明"为什么失败" (批次未分配 / 库存不足),
        不是泛泛"操作失败"
     b) Sticky: error toast 不应 3s 自动消失. 必须 duration:0 + showClose 让用户
        手动关 — 否则用户还没读完就错过关键信息
     c) Next action: 最理想文案提示"先做 X 再重试" (actionHint 字段),
        至少 message 本身必须足够具体让用户能推断出依赖动作
   - 判定:
     * 文案具体 + sticky + 可推断 next action → UX 合格
     * 文案具体但 3s 闪过 → Bug UX (用户可能错过)
     * 文案泛泛 "失败" → Bug UX (用户懵)
     * silent (无 toast) → 严重 Bug
   - 工具: MutationObserver 抓到后, 额外检查:
     - item.cls.includes('is-closable') → showClose 生效 (ElMessage)
     - ElNotification 不用 'is-closable' class, 看是否有 '.el-notification__closeBtn' 子节点
     - 操作后等 5s 再读 log, 看 toast 是否还在 → sticky 验证

9. 数据类页面 byte-match 不够 — 必须做业务合理性抽检 (Bug #37 教训)
   - 定义: 图表 / 表格 / 列表类页面 (不是单一表单/详情), 数据从上传或 seed 来
   - 陷阱: API 返回 22 行 → UI 显示 22 行 → byte-match 通过, 但前 3 行可能是 Excel
     序号列 / 表头行 / 注释行被误当数据 (Bug #37 真实发生).
   - 规则: Top N byte-match 只证明"传输无损", 不证明"数据有意义".
     必须额外抽样:
     a) 中段行 (index = len/2) — 避开 Top 和 Bottom 都是特殊值的可能
     b) 末段 2-3 行 (最后一个数据 + 最后两个) — 特别看是否混入了注释行/合计行
     c) 业务语义抽检: name 是否看起来像真实业务实体 (门店名/商品名/客户名),
        而不是 "1.0/2.0/..." 纯数字, 不是 "门店名称" 这种表头字, 不是 "注：..." 开头
   - 判定:
     * Top 3 + 中段 + 末段都是合理业务数据 → 可信
     * Top 3 OK 但末段混入纯数字/表头/注释 → 数据脏 bug (如 Bug #37)
     * byte-match 过但业务语义异常 → 后端 aggregation 层未过滤 pseudo-rows
   - 为什么这条重要:
     "Top 3 revenue 正好是 6 位数带小数所以匹配" 可以是巧合, 不是证明
     (Bug #34 原报告的陷阱). 至少 3-5 行抽检才能对抗巧合.

诚实输出核对表: 哪些步骤达 deep 标准, 哪些只是 smoke, 哪些是 medium.
禁止把 smoke 当 deep 报告.
禁止把"系统层观察到错"等同于"用户体验正常".
禁止跳过流程依赖错误的 UX 检查.
禁止仅凭 Top N byte-match 断言"数据正确" — 必须 sample 中末段.


专章: 为什么需要强 UI 反馈

流程依赖错误不是系统 bug, 是合理业务规则拒绝. 但对用户体验来说:

1. 错误原因必须显示具体 — 不能只说"发货失败",要说"因为批次未分配"
2. Toast 不能闪过 — 3 秒自动消失不够,用户还没读完就没了
3. 最好指引 next action — 告诉用户"请先点分配批次"

为什么 ERP 流程系统特别重要:
ERP 这种一步接一步的系统, 上游没完成下游卡住是高频现象:
- 发货需要先分配批次
- 开票需要先确认发货
- 收款需要先开票
- 报工需要先下达生产
- 审批需要先提交

每个阻断都是用户疑惑的时刻. 若 UI 反馈不足, 用户:
- 不知道错在哪 → 乱点
- Toast 闪过错过关键字 → 反复点同一按钮, 反复失败
- 不知道 next action → 向客服/同事求助, 浪费时间

最小 UX 实现 (方案 A — 已在本项目实施):

// web-admin/src/api/request.ts
const showMessage = async (message, type) => {
  const { ElMessage } = await import('element-plus');
  ElMessage({
    message, type,
    duration: type === 'error' ? 0 : 3000,   // error sticky
    showClose: type === 'error',              // 手动关
  });
};

进阶方向 (未做, 规划):
- actionHint 字段: 后端错误响应加 "actionHint": "请先分配批次" +
  "actionUrl": "/sales/orders/xxx", 前端用 ElNotification 带按钮跳转
- 流程图标识: UI 上把被依赖的上游按钮高亮/pulse 提示用户先点它
- dialog 替 toast: 关键业务错误用 ElMessageBox.alert (阻塞) 代替 ElMessage,
  用户必须显式点"确认"


第二步: 真端到端执行规则

无论测什么模块, 尽可能按业务线串联方式走, 不是模块独立打点:

- 新建数据优先: 能新建不用 seed. 避免拿历史旧数据假装验证.
- 数据穿越: 上游模块操作完, 立即切到下游模块 (或源头详情页) 验证关联字段回写.
  如 SO → PO → 生产 → 发货 → 开票 → 收款, 每步都要证明"前一步的产出进了这一步".
- 多账号切换: ERP 业务通常要跨 sales/finance/purchase/warehouse/production/operator/foreman
  角色. 真端到端测试必须切号, 不能全程用 factory_super_admin 一把梭.
- 具体单号落地: 每步记下 evidence — orderId / PO 号 / 发货单号 / invoiceNumber /
  toastText / API status / 跨模块关联字段值. 不记"操作成功", 要记"SO-202502-XXX
  confirm 成功, status CONFIRMED, 时间线 +1 事件".
- 错误路径也要测: 成功路径跑通后, 至少主动触发 1 次错误 (如: 库存不足发货/
  重复提交/空字段提交/权限越界), 按 Rule 8 检查 UX 完整性.


第三步: Depth 标签 + 监控证据

每个测试步骤强制打 depth 标签. 分两个正交维度, 不是单一阶梯:

维度 A — 主路径深度 (按测试力度递增, 选 1):
  - smoke: 只打开页面看渲染 / 按钮存在
  - medium: 填表 + submit + API 200
  - deep: 填表 + submit + toast 文案精确捕获 + 列表 +1 精确 + 详情页字段回读
    · 写操作: deep 必须同时满足 Rule 11 roundtrip 3 步 (抓 body + shape audit + re-GET diff)
    · 只读操作: observable 级 deep 已足够 (roundtrip 对 GET 无意义)

维度 B — 错误路径 (正交, 与 A 共存):
  - error-deep: 触发业务错误 + toast 文案 = 后端 message + console 4xx + network
    response.data.message 四匹配 + sticky / showClose 校验
    · 任何写操作必须叠加 1 条 error-deep, 独立于维度 A 的深度选择

至少 1 条 deep (维度 A). 光 smoke 堆数量不算真测试, 是 Rule 1 违规.
如果任务涉及写操作, deep 必须达 roundtrip 级 + 至少 1 条 error-deep.

反模式: 宽松断言 (v2.4 教训)
  ❌ if (autoFilled) recordPass('A'); else recordPass('B');  // 两分支都绿
  ✅ assertThat(precondition).then(specificBranch must fire).otherwise(skip)
两分支都记 PASS 等于该路径无约束, 未测分支静默通过. 永远用单向强制断言:
"给定条件 X, 必须触发 Y" — 不是 "if X then A else B 都算赢".

每步必做 (7 项):

1. 操作 → browser_click / browser_type (真 Locator API)
2. 等待响应 → browser_wait_for
3. browser_snapshot (看新状态)
4. browser_console_messages level=error (监控红色)
5. browser_network_requests (验证 API + URL)
6. 记录 evidence (单号/toast/status)
7. UI 文案抓取 (用 MutationObserver, 不是 querySelectorAll):
   - 操作前安装 observer (只装一次, 跨多步复用)
   - 操作后读 window.__toastLog


特别规则: 错误触发时的四位一体检查

发生 4xx / 5xx / 业务拒绝 时, 必须同时核对:

  a) network response.data.message (后端真实原因)
  b) UI toast 文案 (用户看到的)
  c) toast 生命周期: sticky (duration:0) or 3s 闪过?
  d) toast 是否含 next action 指引 (至少 message 足够具体)

判定矩阵:

| a=b       | c=sticky     | d=具体        | 结论                        |
|-----------|--------------|---------------|-----------------------------|
| 是        | 是           | 是            | 完美 UX                     |
| 是        | 否 (3s 闪过) | 是            | Bug UX — sticky 缺失        |
| 是        | 是           | 否 (泛泛)     | Bug — 后端 message 要补细节 |
| 否(fallback)| 任意       | 任意          | Bug 严重 — 前端吞 message   |
| 无 toast  | —            | —             | 最严重 — silent failure     |

例子:
  network: 400 {"message":"发货行 51 未完成批次分配, 无法确认发货"}
  UI toast: "发货行 51 未完成批次分配, 无法确认发货" (sticky, 有 close btn)
  → 四位一体通过 (注意 message 隐含 next action: "去分配批次")


第四步: 发版前完整性回归 (v2.3, Apr 20 事故触发)

Rule 1-9 管"单个测试深不深", 不管"发版前老功能烂没烂".
Apr 20 客户复测 30min 提 14 bug, 全在下面 5 条盲区 — 每条都是硬规则.

Rule 10 — 最小 body API 测试
Spring @Valid 在 controller auto-fill (setFactoryId / setDate) 前跑,
entity 上的 @NotBlank / @NotNull 会把 null 字段 reject. 开发者用"完整
body" 测 API 永远碰不到, 但前端 dialog emit 的 body 就是缺字段.
硬规则: 每个 POST /create 必须按前端 emptyForm() 的字段集跑一次测试.
如果返 400 "xxx 不能为空" 而 controller 里本来就 auto-fill → 删 entity
的 @NotBlank/@NotNull (DB NOT NULL 保兜底). 共享 DTO (create+update 同
一 DTO) 同理 — BR-13 CreateUserRequest 被 PUT 复用, username @NotBlank
对 update 误报.

Rule 11 — Read-after-write 硬校验 (v2.4 升级为 wire+roundtrip)
写接口测试必 3 步:
  ① 操作前 `page.on('request', ...)` 捕 HTTP body, 记 keys 期望集
  ② 发 POST/PUT → 验 2xx + success=true + **payload shape audit**:
     - 无 phantom 字段 (URL path 已有的 factoryId / batchId 不应再塞 body)
     - 无 backend 管的字段 (id/createdAt/updatedAt/*_name derived field)
     - required 字段全在 (对齐后端 DTO @NotBlank/@NotNull)
  ③ 独立 GET 被改资源 → 逐字段 diff: 发送值 === 持久化值?
     任何字段 diff = silent-drop bug (backend mapper 漏 map, 或 @Transient
     setter 伪更新, 或 @Column(updatable=false)).
     注意: re-GET 前若端点有读 cache, 先 wait cache TTL 或加
     `Cache-Control: no-cache` header, 否则 cache 返旧值会误判 silent-drop.

真实事故:
- BR-13: UserMapper.updateEntity 不 map roleCode → PUT 200 但 DB 没变
- W-04 (Round 8): MaterialBatchMapper.updateEntity 漏 map 4 字段
  (receiptQuantity / quantityUnit / totalWeight / expireDate) → PUT 200
  success=true 但全部原值, 只有 notes 被更新. 观察层 "toast + 列表"
  测试永远抓不出, 只有 re-GET diff 能抓.
- W-05 (Round 8): FE `{ ...form, factoryId }` 把 URL path 变量塞 body
  → Jackson 当前配置静默丢弃, 但若未来开 FAIL_ON_UNKNOWN_PROPERTIES
  严格模式这类 phantom 字段会 400, 须提前清理

适用: 所有写接口 (POST create / PUT update / PATCH / 批量导入), 角色
/权限变更, 订单状态 transition, 字段 patch, 库存调整.

Rule 12 — 发版前 5 项 checklist (30min 人工 + grep)
12.1 每个 list.vue 必有 keyword 搜索 + 状态过滤 + 搜索/重置按钮 + 空状态
     + 分页. grep: find views -name list.vue | xargs grep -l searchKeyword
12.2 后端 enum 改动同一 PR 必扫前端硬编码:
     grep -rn "roleOptions\\|const ROLES\\|STATUS_OPTIONS" web-admin/src
     长期应改为前端动态拉 /enums/{name} API.
12.3 每个 dashboard 的 statCards.route 必须点一次, 落地页筛选与卡片
     标题语义一致 (BR-03 "待审批"卡片应带 ?status=SUBMITTED).
12.4 创建 dialog 宽度核算: N 列宽 + (N-1)×8 gap + 40 padding ≤ dialog
     width. 1366×768 / 1920×1080 都看一眼.
12.5 浏览器边缘: 请求中点回退不应弹 "canceled" toast (interceptor 要
     axios.isCancel / ERR_CANCELED 静默 reject); token 过期自动 refresh;
     多 tab 状态一致.

Rule 13 — 用户 shadow test (最关键, 性价比最高)
每个大版本 prod 发版前, 找一个**真实非开发用户** (客户/实施/QA) 自由
点透 20-30min, 记录所有不顺的地方. 格式就是本项目 Apr 20 doc:

  首页-经营驾驶舱-回退   报错   canceled
  首页-今日领料单-新建   报错   创建失败,不能为空
这比 100 个自动化 E2E 都有效 — Apr 20 14/14 都来自一个人 30min.

Rule 14 — 发版管理 (防用户缓存续命)
用户浏览器缓存老 bundle 会让已修 bug 看似复发 (BR-08/09 Apr 18 已修
Apr 20 又报). 最小方案: build 时 inject version, 前端定期 fetch

以下 3 条 (Rule 15-17) 是 v2.4 新增, 对应 confirmation bias 盲区 / 入口点真空 / 静态结构性 bug — 补 Rule 1-14 的 "动态观察" 层面之外的 3 个维度.


Rule 15 — 独立 reviewer + 同模式扫荡 (confirmation bias 防护, v2.4)
自测有 confirmation bias — 我设计的 test 证明我相信的事, 漏测的就是我回避
的问题. Round 7 session 自测 27/27 绿灯, superpowers:code-reviewer agent
秒抓 4 Important findings. 独立 agent 是性价比最高的 bug 发现手段.

硬规则:
  a) 触发条件: 每 3+ 个 logic commits (不含 docs/rename/config-only)
     或每个 feature/bug batch 完成, 必跑一次 superpowers:code-reviewer
     (Task tool, zero conversation context).
  b) Reviewer 发现的每个 pattern 立即去扫 sibling 代码 — 不是记 backlog
     留到"下轮再做". Pattern = 可 grep/归纳的反模式, 如 "@RequestBody
     Entity 直绑"、"partial-field mapper 漏 null-guard"、"FE `{...form}`
     spread 带 phantom 字段".
  c) 扫荡产出 = pass/fail 列表, 每个 match 标 "vulnerable / safe /
     needs-verify". vulnerable 要么修, 要么写具体 test 计划进 backlog
     (具体到 file:line + 测试设计, 不是 vague "以后").
  d) 自我审查不能取代独立 reviewer — 自我 critic 写的 "challenge" 都是
     softball question, 答案提前在心里.

真实事故:
- Round 7 reviewer I-2 ("edit path 没测") + I-4 ("FE payload 带 phantom")
  → Round 8 把这两个 pattern 去扫 material batch edit + 所有 warehouse
  POST body → 立即抓到 W-04 P1 silent-drop + W-05 cosmetic. 每个
  pattern 产出 1-2 个真 bug.
- 不跑 reviewer 的下场: 27/27 自信发 prod, 客户下个版本必有 complaint.


Rule 16 — 入口点独立覆盖矩阵 (coverage vacuum 防护, v2.4)
同一 Vue 文件 / 同一 form 有多个 entry points (handleCreate / handleEdit /
handleDelete / handleStatusChange), 每个 entry point 独立代码路径独立 bug.
"测了 create flow" ≠ "测了该模块".

前置条件: 本规则仅在 form reset 逻辑写在 entry function 内 (handleCreate
重置 formData + flag) 时适用. 若 dialog 用 `@open="resetAll()"` 或
`destroy-on-close` 保证每次重建, 状态泄漏不可能发生, 可跳 Rule 16b.

硬规则:
  a) 任何 CRUD list.vue, 至少覆盖 create + edit + 1 个 status transition.
     扫描示意: 找 Vue SFC 里的 `function handleX` 或 `const handleX = () => {}`
     入口函数集合 (用 IDE 的 "find in files" 或在项目根跑
     `find web-admin/src/views -name "*.vue" | xargs grep -E "(function|const|let) handle\\w+"`
     — 避免依赖 bash globstar, 参考 Rule 17 WHAT+WHY 的写法)
  b) 同 form 共用字段但 reset 逻辑独立 → 对每个 entry 独立测 state isolation.
     e.g. Round 7 I-2: materials/list.vue handleCreate 重置 w02HintShown
     但 handleEdit 漏. 测试矩阵:
     |              | 第一次开 | 第二次开 | 第一次开A→关→开B |
     | handleCreate | ✓       | ✓       | n/a              |
     | handleEdit   | ✓       | ✓       | n/a              |
     | A→B 跨 entry | n/a     | n/a     | ✓ (state 不泄漏) |
     (n/a = 该维度对该 entry 不适用, 不是"可省略")
  c) 取数/prefill 在每个 entry 独立验证: create 空表单 / edit 预填 /
     cancel 后 re-open 不留旧值.

真实事故:
- Round 7 handleEdit 漏 `w02HintShown = false` (I-2) → 编辑未配单价原料
  hint 不再显示. Round 8 Phase A 直接测 edit 路径即暴露.
- Round 8 Phase C cross-dialog state test: create cancel + edit open 验证
  form 不留旧 dirty 值.


Rule 17 — 后端反模式 checklist (静态扫补 E2E 盲区, v2.4)
E2E 跑再多也跑不出"只有读代码才能看出"的结构性 bug. 每发版前 6 条检查, 有
hit 就深挖. 完整 grep/ripgrep 模式见 `scripts/qa/static-scan.sh` (随 v2.5
或按需手写), 这里列 WHAT + WHY, 不列 HOW 的 shell 细节 (各平台 glob/转义
差异大, 命令容易开箱就错).

17.1 @RequestBody 直绑 Entity (W-01 根因, reviewer S-2 还有多处)
     目标: Controller 方法参数是 entity class (ShipmentRecord,
     MaterialBatch 等), 不是专用 Request DTO (以 Request/DTO/VO 结尾).
     风险: entity 的 @NotBlank/@NotNull 在 controller auto-fill
     (setFactoryId/setDate) 之前跑, FE 缺字段 → 400 100% 失败.
     修: 改用专用 Request DTO 隔离 wire contract 和 persistence model.

17.2 Mapper partial-field updateEntity (W-04 根因)
     目标: mapper 类里的 update*(<Entity>, <Request>) 方法, 对比
     <Request> 可编辑字段集看 update 方法是否 null-guard 映射全部.
     风险: 漏 map 的字段 = silent-drop bug (PUT 200 但 DB 不变).
     修: 每个 DTO editable 字段加 `if (req.getX() != null) entity.setX(req.getX());`

17.3 @Transient 字段/getter 上的假 setter 调用 (v2.4 教训)
     目标: entity 里 @Transient 字段 (或 @Transient 修饰的 getter, 两种写法
     都表示计算属性无对应 @Column); mapper/service 里有没有调 Lombok
     @Data 生成的对应 setter.
     风险: setter 写 field 变量但 Hibernate 不持久化 — 永远 silent-drop.
     修: 计算属性不能被 set, 要派生存储字段 (见 W-04 totalWeight →
     weightPerUnit 派生).

17.4 FE form spread 带 phantom 字段 (W-05, I-4)
     目标: Vue 里 `...form.value` 或 `...formData` 塞 submit payload 时,
     检查 form ref 的 initial fields 是否都应该上 wire. UI 不显示但保留
     的字段 = phantom.
     风险: Jackson 静默丢 (现在) / FAIL_ON_UNKNOWN 开后 400 (未来).
     修: submit 前 destructure 剔除, 或重构为 computed payload builder.

17.5 Semantic delta vs absolute 混淆 (W-03 根因)
     目标: /adjust /delta /increment /调整 endpoint 的后端 param 语义
     (newQuantity / delta / amount) 是否和 UI 输入意图对齐.
     风险: UI 显示 "调整数量 正=增负=减" 但后端当 newQuantity, 正数变成
     "重置为该值" — 数据完整性灾难.
     修: FE `newX = current + delta` client-side 派生, 或后端加 mode
     param 区分 ABSOLUTE/DELTA.

17.6 共享 DTO 被 create+update 复用 (BR-13 模式, 配合 Rule 10)
     目标: CreateXRequest 同时被 POST /x 和 PUT /x/{id} 绑定.
     风险: create 必填的 username @NotBlank 对 update 误报 (update 不需
     要 username, 只改 roleCode). 见 Rule 10 最小 body 测试.
     修: 拆 UpdateDTO, 或弱化 Create DTO 的 validator 用 Groups.

Bug 记录标准 (5 类)

发现任何 bug 立即:
1. 记 Task (TaskCreate) — 标题带模块 + 症状
2. 分析疑似根因 (查 service 代码 / Java log / DB constraint / 前端 catch 块)
3. 不草率关闭, 不假装已修

Bug 分类 (6 类, 不要混并):
- 业务逻辑 bug: 后端 API 返错/返错数据
- silent-drop bug (v2.4, 独立类): 后端 HTTP 2xx success=true, 但部分字段
  未持久化 (mapper 漏 map / @Transient 伪 setter / @Column updatable=false).
  用户无任何错误反馈但下次看数据没变. 只能靠 roundtrip re-GET 抓. 真实
  事故: BR-13 (roleCode) / W-04 (4 字段)
- UX bug: 后端 OK 但前端吞错误 / 显示 fallback / silent failure / toast 不准确 /
  toast 非 sticky (用户错过) / 缺 next action 指引
- RBAC bug: 权限矩阵和 UI 按钮可见性不一致
- 数据一致性 bug: 跨模块回写丢失 / Tab 计数不对 / 时间线缺子事件
- 流程事故 bug: deploy 误操作 / 并发 session 覆盖 / 脚本默认值危险 /
  非原子 DB 操作破坏一致性
