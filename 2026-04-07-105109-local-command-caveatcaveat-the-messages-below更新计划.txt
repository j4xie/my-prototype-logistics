  ---
  为什么 GitHub 镜像不行 — 详细分析

  根本原因：j4xie/my-prototype-logistics 是 private 仓库

  证据链

  1. 三个不同 GitHub 源下载到完全一致的 9 字节文件
    - GitHub 直连、ghfast.top、gh-proxy.com → MD5 全部
  9d1ead73e678fa2f51a70a933b0bf017
    - 网络/CDN 问题不可能让三个独立源拿到字节完全一致的文件
  2. 9 字节内容是字面文本 Not Found（不是真正的 404 状态码）
  3. API 验证仓库可见性: gh api ... --jq '.private,.visibility' 返回 true /
  private
  4. gh CLI 带 token 能正常下载（已下到 37MB+ 验证可行）

  GitHub 镜像的工作原理

  普通用户 → 镜像 (ghproxy.cc / ghfast.top / cf.ghproxy.cc 等)
                ↓
                对 GitHub 发起公开 HTTP 请求 (无 token)
                ↓
  public repo  → 拿到文件 ✅
  private repo → GitHub 返回 "Not Found" 文本 (HTTP 404) ❌
                ↓
                镜像原样转发 → 你拿到 9 字节 "Not Found"

   完全无效。

  你测试镜像能走通的原因

  - 你测试时八成用的是 public 项目（如 git clone 大型 OSS 项目）
  - 或者你用了 gh release download（gh CLI 自动带 token）

  private repo 完全失效，但脚本完全不知道。

  GitHub 镜像问题最终结论

  ┌──────────────────┬────────────────────────────────────────────┐
  │       假设       │                  是否成立                  │
  ├──────────────────┼────────────────────────────────────────────┤
  │ 镜像服务挂了     │ ❌ 三个独立镜像 MD5 完全一致，不可能同时挂 │
  ├──────────────────┼────────────────────────────────────────────┤
  │ CDN 缓存了旧文件 │ ❌ tag 是新生成的，不可能有缓存            │
  ├──────────────────┼────────────────────────────────────────────┤
  │ 网络问题         │ ❌ 服务器从 GitHub 直连 4MB/s              │
  ├──────────────────┼────────────────────────────────────────────┤
  │ 仓库是 private   │ ✅ gh api ... .private = true              │
  └──────────────────┴────────────────────────────────────────────┘

  private repo 下，所有镜像都通过无 token 的公开 HTTP 访问 GitHub release
  asset，GitHub 返回的不是真正的 404 状态码，而是带有字面字符串 Not Found 的
  HTTP 200 响应（9 字节）。这就是为什么三个源 MD5
  完全一致：9d1ead73e678fa2f51a70a933b0bf017 = md5("Not Found")。

  真实瓶颈是你的本地上行带宽

  实测 1.3 MB/s 远低于 OSS 加速理论 5-10 MB/s。OSS
  加速节点已经在干活，但被你本地上行带宽卡住。即使如此，比 scp 直传快 22
  倍是因为：

  1. OSS 加速节点是 anycast，自动连接最近的边缘节点（毫秒级 RTT），TCP
  窗口能开到很大
  2. scp/ssh 是单一长连接到上海（几十毫秒 RTT），TCP 窗口受限于 BDP（带宽×延迟）
  3. 服务器从 OSS 内网下载几乎免费且
  100MB/s，所以全程瓶颈只在你本地→边缘节点这一段

  根本原因分析

  这不是 rsync 的问题，是你本地到服务器的 SSH 通道本身有问题：

  ┌──────────────────────┬──────────────────────┬────────────┐
  │         协议         │       之前实测       │    现象    │
  ├──────────────────────┼──────────────────────┼────────────┤
  │ scp (单向流)         │ 60 KB/s 龟速但能跑完 │ 慢但稳     │
  ├──────────────────────┼──────────────────────┼────────────┤
  │ ssh + cat (单向流)   │ 60 KB/s 龟速         │ 慢但稳     │
  ├──────────────────────┼──────────────────────┼────────────┤
  │ rsync (双向 stream)  │ 直接 RST 或卡死      │ 完全不可用 │
  ├──────────────────────┼──────────────────────┼────────────┤
  │ OSS 加速（不走 SSH） │ 1.3 MB/s             │ 稳定       │
  └──────────────────────┴──────────────────────┴────────────┘

  rsync 用的是 SSH 通道里的双向流协议（一边发数据，一边收
  ack/checksum），这种交互模式触发了你网络路径上某个中间设备的限速或
  RST。可能是：
  - ISP 对 SSH 长连接的限速 / 老化
  - 中间防火墙对 SSH stream 的 deep inspection
  - 阿里云入口的 anti-DDoS 误判

  简单的 scp 单向流能跑完只是因为它没有反向 ack，所以中间设备不会主动
  reset；但速度也被压到 60 KB/s，证明同一个网络问题。

  结论

  rsync 这条路在你当前的本地网络下不可行。即使二进制修好了，也用不了。

  OSS 加速能跑 1.3 MB/s 是因为它走的是 HTTPS 到 CDN 边缘节点，完全绕开了你的 SSH
   慢通道。

  接下来怎么办

  ┌────────────────────┬─────────────────────────────────────────────────────┐
  │        选项        │                        价值                         │
  ├────────────────────┼─────────────────────────────────────────────────────┤
  │ A. 接受现状        │ 你已经有 OSS 加速通道，1.3 MB/s × 150MB = 2         │

  ├────────────────────┼─────────────────────────────────────────────────────┤

  ├────────────────────┼─────────────────────────────────────────────────────┤

  ├────────────────────┼─────────────────────────────────────────────────────┤

  └────────────────────┴─────────────────────────────────────────────────────┘

  Java 锁定问题根因

  PID 53440 用 java -jar 启动 fat jar：
  java.exe -Xms512m -Xmx1280m -jar .../target/cretas-backend-system-1.0.0.jar
    --spring.profiles.active=pg,dev
    --spring.jpa.hibernate.ddl-auto=none
    --spring.datasource.url=...
    --server.port=10010

  JVM 用 mmap 持续映射 fat jar 文件 → Windows 永久锁定 → mvn package 的
  repackage 阶段无法 rename 旧 jar → 部署失败。

  解决方案：改用 mvn spring-boot:run

  mvn spring-boot:run 不打 fat jar，直接从 target/classes/ 加载 .class
  文件。class 文件加载后 JVM 不持有 file handle（与 jar 的 mmap
  不同），所以完全不锁 fat jar，下次 mvn clean package 可以正常跑。

  新启动命令（直接替换你 memory 里的那条）：

  cd backend/java/cretas-api && \
  DB_PASSWORD=cretas_pass POSTGRES_SMARTBI_PASSWORD=smartbi_pass \
  JAVA_HOME="C:/Program Files/Zulu/zulu-21" \
  ./mvnw.cmd spring-boot:run \
    -Dspring-boot.run.profiles=pg,dev \
    -Dspring-boot.run.jvmArguments="-Xms512m -Xmx1280m" \
    -Dspring-boot.run.arguments="--spring.jpa.hibernate.ddl-auto=none --spring.d
  atasource.url=jdbc:postgresql://localhost:5432/cretas_db?sslmode=disable 
  --server.port=10010"
