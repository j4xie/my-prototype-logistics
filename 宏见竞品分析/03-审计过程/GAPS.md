# 宏见有 / Cretas 缺 — 纯缺口清单

> 从 4 轮审计中剥离出的具体差距。**只列"宏见做得好且 Cretas 真缺"的**，不重复 STRATEGY 战略层讨论。
>
> 每条含：(a) 是什么 (b) 视频/音频证据 (c) Cretas 现状 (d) 借鉴成本/优先级

---

## 一、🔴 核心业务能力缺口 (P0-P1, 真正缺的)

### G1. 报价单 → 销售订单转化链路
- **是什么**：销售先发报价单给客户（含商品明细 + 价格 + 有效期），客户接受后报价单一键转销售订单
- **证据**：音频 11:00-11:12，"销售订单可以直接下，也可以通过报价单去生成"
- **Cretas 现状**：❌ 完全缺失，没有 Quote/Quotation 实体或前端
- **借鉴成本**：5-8 人天（实体 + Service + 前端 + AI Chat 集成）
- **优先级**：**P0** — 销售流程的起点，没有这个，"对话式销售"故事不完整

### G2. 同产品 × 多客户价目表记忆
- **是什么**：客户 A 历史买这个产品都是 100 元，下次给他建单自动带 100；客户 B 是 95 元自动带 95
- **证据**：音频 10:42，"同一产品针对不同客户的不同价格,他会自动记录到销售订单上面"
- **Cretas 现状**：❌ `PriceListScreen.tsx` 有价格表入口但无按客户的记忆
- **借鉴成本**：2-3 人天（建表 + 创建销售单时查询并自动建议）
- **优先级**：**P0** — 食品行业谈判常态

### G3. 采购订单二次处理（请购→分供应商拆单）
- **是什么**：生产提交请购单 → 采购审批后**按供应商拆成 N 张采购单**（同一物料分给 3 个供应商）
- **证据**：音频 3:04-3:21，"针对这个请购的需求,请购单也是一样会做一个二次处理,把它针对性的分供应商去转化成采购"
- **Cretas 现状**：❌ PurchaseOrderCreateTool 是单 PO 创建，无"按供应商拆分"逻辑
- **借鉴成本**：3-5 人天
- **优先级**：**P1** — MRP 链路的关键节点

### G4. 月度考勤可视化矩阵
- **是什么**：员工×日历 颜色矩阵（绿=正常 / 黄=迟到 / 红=旷工 / 蓝=加班 / 灰=休 / 粉=请假 / 橙=出差）一目了然
- **证据**：帧 `001653`（月报）+ `001707`（日报），整月 30+ 列 × 员工行
- **Cretas 现状**：⚠️ TimeClock 实体存在但**无月度矩阵汇总视图**
- **借鉴成本**：3-5 人天（聚合 API + 前端日历组件 + 颜色编码）
- **优先级**：**P1** — 客户原话"管理这些数据类的可能就是管理层在做"——管理层就要这种汇总视图

### G5. 请假/调休/报销/工作日报
- **是什么**：员工自助提交请假、调休、报销、日报；走简单审批流
- **证据**：音频 15:23-15:34，"做请假,做调休,做报销,做工作日报"
- **Cretas 现状**：❌ 这 4 个都缺；只有 TimeClock 打卡
- **借鉴成本**：每个 3-5 人天 × 4 = 12-20 人天
- **优先级**：**P1** — 客户实际使用频率高（每天每个员工都要碰）

### G6. 行级状态色块（整行背景色）
- **是什么**：列表行用浅色背景表达 status（粉色=进行中 / 浅绿=已完成 / 浅黄=待审批 / 红=异常）
- **证据**：帧 `000122` `000423` `001435`，所有列表都这样
- **Cretas 现状**：⚠️ 仅在部分列表用 status chip 标签；扫描友好度低
- **借鉴成本**：1-2 人天（修改列表组件的 row style）
- **优先级**：**P1** — 低成本高 ROI，立即可做

### G7. 客户跟踪记录 + 文件附件
- **是什么**：每个客户的拜访记录、电话记录、合同/营业执照/价格表 PDF 附件
- **证据**：音频 9:42-9:54，"都是可以去填写他的一个跟踪记录啊,包括他客户的一个文件和图片这些内容"
- **Cretas 现状**：❌ 仅 Customer 实体存在；无 customer_followup 表 + 无附件上传
- **借鉴成本**：3-5 人天
- **优先级**：**P1** — 客户原话"主要 4 部门：销售/采购/仓库/生产"，销售部门要这个

## 二、🟡 UI/UX 设计细节缺口 (P1-P2, 低成本高效果)

### G8. 底部固定批量操作栏
- **是什么**：列表多选时底部固定栏出现 "批量提交生产 / 批量提交采购 / 批量提交外购 / 添加资料 / 生成请购工单 / 生成采购工单" 6 个按钮
- **证据**：帧 `000122`，物料需求按工序页面底部
- **Cretas 现状**：⚠️ 仅 selection mode 才出现，未做成"标配下沿固定"
- **借鉴成本**：2-3 人天（重构 list bottom action bar）
- **优先级**：**P1**

### G9. 多 Tab 累积导航（Web 端）
- **是什么**：用户每打开一个明细页，顶部多一个 tab；可在多任务间快速切换
- **证据**：帧 `001151` `000423` 等多个帧的顶部 tab 列（有时 7-10 个 tab 累积）
- **Cretas 现状**：❌ 移动优先无此范式；如果出 Web Admin 版需要考虑
- **借鉴成本**：仅 Web 版需要，5-8 人天
- **优先级**：**P2** — 仅当 Cretas 做 Web 端时需要

### G10. 分块表单 + 实时汇总
- **是什么**：表单分多个 section（基本资料/明细/价格/审批配置），底部固定显示"金额合计"实时计算
- **证据**：帧 `000949` `000745` 销售单/采购单创建页底部
- **Cretas 现状**：⚠️ 部分表单（成本分析）有汇总，但创建类表单无
- **借鉴成本**：2-3 人天（每个 create 表单加 sticky footer summary）
- **优先级**：**P1** — 让数据录入更易感知正确性

### G11. 多维度库存联动筛选
- **是什么**：库存查询页顶部筛选器联动 (产品 → 批号 → 供应商 → 日期范围 → 失效期范围)，每改一个其他选项联动
- **证据**：帧 `001435`，20+ 筛选 + 列
- **Cretas 现状**：⚠️ InventoryQueryScreen 有筛选但维度少于宏见
- **借鉴成本**：3-5 人天（扩展筛选 + API 参数）
- **优先级**：**P1** — 食品行业刚需

### G12. 弹窗内联二维码 / 工序说明
- **是什么**：列表行点击"扫码"图标，弹窗显示**该单据专属二维码 + 工序说明**，工人手机扫码后进入对应操作页
- **证据**：帧 `000553` 生产任务列表中央的 QR 弹窗
- **Cretas 现状**：⚠️ LabelScanScreen 在，但生产任务/领料单等业务实体未生成 QR
- **借鉴成本**：2-3 人天（ProcessingBatchCreate 自动生成 Label + 扫码后路由）
- **优先级**：**P0** — 直接对应客户痛点（"老员工不会操作"，扫码即操作）

## 三、🟢 行业深度细节缺口 (P1, 食品厂场景必须)

### G13. 制效天数告警
- **是什么**：每个产品设置"距失效期 X 天预警"，到了系统自动标红
- **证据**：音频 14:08-14:21，"我们会有一个制效天数的一个设置 ... 超过多少天系统会标普"
- **Cretas 现状**：⚠️ MaterialBatch 有 `expireDate` 字段，但**无 expiryWarningDays 配置和定时告警**
- **借鉴成本**：2-3 人天（cron job + 告警写入 AlertScreen）
- **优先级**：**P0** — 食品行业刚需（盒马山姆审计要求）

### G14. 多仓库 × 多批号 × 多供应商 × 多失效日期 库存细分
- **是什么**：同一物料因为不同仓库 / 不同批号 / 不同供应商 / 不同失效日期被记为**不同库存数量**
- **证据**：音频 12:50-13:34，详细解释这种"4 维度分别记账"
- **Cretas 现状**：✅ MaterialBatch 实体支持 batchNumber/supplierId/expireDate/warehouseId 四维度——**实体层已有 75%**
- **借鉴成本**：⚠️ 实体齐，但**前端聚合查询 UI 和分维度统计 API 缺**，2-3 人天
- **优先级**：**P1**

### G15. 指定批次出库 vs FIFO 默认
- **是什么**：领料/出库时，默认 FIFO（先进先出）；如需指定批号可手动选择
- **证据**：音频 13:52-14:05，"可以...如果没有指定批次的情况下就是现金现出"
- **Cretas 现状**：⚠️ MaterialFifoRecommendTool 是"推荐"模式，**未实现强制 FIFO 出库 + 可覆盖**
- **借鉴成本**：2-3 人天
- **优先级**：**P1** — 食品行业出库逻辑核心

### G16. 多仓位 (bin-level)
- **是什么**：仓库内细分到"A 区 3 排 5 号货架"，扫码定位
- **证据**：音频 12:47-13:16
- **Cretas 现状**：❌ 仅 warehouseId，无 binLocation
- **借鉴成本**：5-8 人天（实体 + 出入库流程改造）
- **优先级**：**P2** — 大型仓库才需要

### G17. 质检项目和参数自定义模板
- **是什么**：每个产品类型可配置自己的质检项 + 参数标准（蛋白质 ≥ 18g / 含水量 ≤ 5% / 微生物菌落数 ≤ 1000）
- **证据**：音频 12:00-12:14，"支检项目和支检参数都可以用我们自己去设置"
- **Cretas 现状**：⚠️ `QualityCheckItemDetailScreen` 在，但**无产品-质检模板绑定**
- **借鉴成本**：3-5 人天
- **优先级**：**P1** — 食品质检合规需求

### G18. 小组长代报工
- **是什么**：组长一次扫码代报全组 5-10 人的产量（而非每人扫一次）
- **证据**：音频 7:08-7:38，"一组小组长的一个操作了 ... 报工的行为的话,一般是要具体到个人 ... 系统只会记录到组长这个名字上面"
- **Cretas 现状**：❌ ProcessingWorkerCheckoutTool 是单人粒度，无"组长代报"
- **借鉴成本**：2-3 人天（增加 "leadWorkerId + memberWorkerIds[]" 字段 + 工资分摊逻辑）
- **优先级**：**P1** — 客户原话直接采纳过的方案（接受了"组长代报"但表达过虑）

## 四、💰 财务深度细节 (P2-P3, 看客户群)

### G19. 会计凭证模板系统（23 类业务凭证）
- **是什么**：每类业务（应收/应付/销售出库/采购入库/生产领料/委托出库/退货...）有对应的借贷凭证模板，到时间自动生成凭证
- **证据**：帧 `001546`，23+ 行业务凭证模板列表 + "自定义模板" tab
- **Cretas 现状**：❌ 只有 ArApTransaction 流水，**无 voucher_header / voucher_line / ledger_account / journal_entry**
- **借鉴成本**：15-20 人天（数据迁移 + 试算平衡 + 期末结账）
- **优先级**：**P3** — 仅当客户群明确要求税务凭证（30+ 人厂通常用代账公司，不需要这么深）

### G20. AR/AP 账龄分析
- **是什么**：应收账款按账龄分组（30 / 60 / 90 / 180 天）+ 应付账款同理
- **证据**：音频 14:35-14:40 "应收应付,还有的记账以及凭证的一个这些功能"
- **Cretas 现状**：⚠️ ArApTransaction 有但无账龄聚合视图
- **借鉴成本**：2-3 人天
- **优先级**：**P2**

### G21. 按单结算 vs 多单汇总对账
- **是什么**：销售订单可选"单单结"或"月底汇总对账单结" 2 种模式
- **证据**：音频 11:23-11:32 "我们支持按单结算,就是你后续的结算的话是按订单结算,还是多个订单给它汇总成一个对账单去结算"
- **Cretas 现状**：❌ 无此模式分支
- **借鉴成本**：3-5 人天
- **优先级**：**P2**

## 五、🛠️ 销售/运营模式细节 (P3, 但启发性强)

### G22. "全功能版本 vs 行业精简版本" Feature Flag
- **是什么**：销售时根据客户行业（食品 / 装备 / 模具）开关功能模块；客户不用看到不相关的"装箱称重 / 设备管理"等模块
- **证据**：音频 17:51-18:14 销售原话"针对您的预算...实际功能需求...合适的功能版本"
- **Cretas 现状**：⚠️ 有 RBAC 和角色，但**未做"行业初始化模板"**
- **借鉴成本**：5-8 人天（AIBusinessInitScreen 已有可扩展 + Feature Flag 中心）
- **优先级**：**P2** — 重要的销售/产品策略问题

### G23. 试用账号 + 派授权线下样板演示
- **是什么**：客户提需求 → 销售（授权）线下来访 → 用客户真实数据建样板 → 客户试用 → 报价 → 签约
- **证据**：音频 19:54-21:30 反复提"派授权..."
- **Cretas 现状**：❌ 销售流程未标准化
- **借鉴成本**：营销/销售流程设计，不是工程问题
- **优先级**：**P3** — 但应当作为 GTM 策略讨论

## 六、不建议借鉴（明确反对）

| # | 项 | 为什么不抄 |
|---|---|---|
| ❌ N1 | 左侧 20+ 二级树形菜单 | 是 1990s ERP 范式。客户原话"论资在论的太多了"就是这个的暴露 |
| ❌ N2 | 顶部 12 横向模块菜单 | 同上 |
| ❌ N3 | 17-Tab 客户详情页 | 信息架构暴露过度 = cognitive overload |
| ❌ N4 | 可视化工作流拖拽编辑器 | PR-driven，客户实际只配置 1 次；用 AIChat 配规则更现代 |
| ❌ N5 | 工作手机 / 微信会话归集（"增值业务"）| 合规边界灰色 |
| ❌ N6 | 节点单据强制流转（请购→采购→出货→入库 N 单据流程） | 这是客户最大抱怨；agent 范式的核心就是替用户编排掉这些 |
| ❌ N7 | 按"全功能 + 砍模块"作为唯一定价策略 | Cretas 应该按角色 + 场景定价，更现代 |

## 八、对比 STRATEGY.md 的修正

STRATEGY §D-1 的"立即做"主要是修 Cretas 自家死代码（17-18 人天），本清单是**新功能**抄宏见（Sprint 1+2 = 39-63 人天）。

**两条路线不冲突，应**并行**：
- 修死代码（STRATEGY D-1, 17-18 天）= 让现有故事可信
- 抄宏见 P0+P1 (Sprint 1+2, 39-63 天) = 补食品厂硬需求

**合计 56-81 人天 ≈ 12-16 周** 让 Cretas 真正可以打这单客户。
