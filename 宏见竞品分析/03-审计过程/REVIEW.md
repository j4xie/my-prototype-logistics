# Fairview Square 演示 — 评审报告 (REVIEW, 非 SUMMARY)

> 对应原 REPORT.md 的不足：原版偏总结演示讲了什么；本版做**判断**——值不值抄、Cretas 真实差距、Agent 方案哪些是 PR 哪些能落地。
>
> **覆盖密度**：283 张精细场景帧 (threshold 0.05) + 471 张密集帧 (3 秒/帧) + 54 gap-fill = 实际看过 ~50 张关键帧。原版仅 37 张漏掉财务凭证模板/考勤矩阵/角色权限 3 个重要页面，本版已补。

## A. 评审框架

评一个 ERP 功能值不值得抄，我用 3 个维度：

| 维度 | 含义 |
|---|---|
| **真实业务价值** | 客户实际会用、且降本/降时的功能 |
| **抄袭成本** | 后端 + 前端 + 数据迁移 + 培训 |
| **是否与 agent 范式冲突** | 我们的核心差异化是"对话式"，传统单据流是它的对立面 |

**关键判断原则**：宏见每出现一个"看起来很好用"的功能，要先问：**这是不是因为他们没有 agent 所以才必须这么做？** 如果是，我们抄它就是给自己挖坑。

## B. 宏见演示功能 — 按"该不该抄"分三档

### 🟢 第一档：必须抄 (核心业务能力，无 agent 也能用)

| # | 功能 | 时间戳 | 为什么必须抄 | Cretas 现状 |
|---|---|---|---|---|
| 1 | **销售单需求 → 一键转生产/采购/外购**（"二次处理"） | 1:22-1:39 | 客户**唯一主动赞叹**的功能。MRP 的脊柱。无论有没有 agent，这个统一缺料分析视图都是 ERP 的核心 | 65% — 后端实体齐，前端无统一视图 |
| 2 | **生产任务专属 QR**（扫码报工/领料/入库） | 5:53 | 即使用 agent，QR 仍是工厂物理世界的入口（手机扫码 < 1 秒）。Cretas 已有 LabelScan 组件 + shipment_label 的 QR 生成 | 30% — 组件在，业务接入未做 |
| 3 | **领料单 BOM 自动展开 + 多列进度**（计划/申请/已领/未领/退料/实领） | 7:47 | BOM 引擎已是 85%，前端列设计是"白拿"。FactoryMaterialRequisition 实体也齐 | 60% — 前端创建页缺自动 BOM 拉取 |
| 4 | **多维度库存查询**（仓×批×供×期 × 失效告警） | 14:35 | 食品行业是命脉。Cretas 已 75%，缺前端聚合查询页 | 75% — 实体齐，无 UI |

### 🟡 第二档：可选抄 (有价值但不紧急，或与 agent 部分冲突)

| # | 功能 | 时间戳 | 评判 |
|---|---|---|---|
| 5 | **可视化工作流节点编辑器** | 0:43 | **看起来很酷但实际客户用不到**。工作流编辑器是给 IT 看的，真实场景下，工厂老板让 IT 配一次就不再动。Cretas 已有 ApprovalChainConfig + Drools，**用 AIChat 让管理员说"销售单超过5万要老板审"自动生成规则**比拖拽编辑器更 agent-native。**抄编辑器是 PR-driven 工程**——优先级 P3 以下 |
| 6 | **会计凭证模板系统** | 15:46 | 23 类业务凭证模板（应收/应付/销售出库/采购入库/生产领料/委托出货/...）。这是真财务功能，不是花架子。但**客户实际是 30-50 人小厂，凭证是给会计交报税用的，不是核心运营**。Cretas 有 ArApTransaction，缺 Voucher 模板系统。**优先级 P2** |
| 7 | **报价单 + 自定义打印模板** | （音频提及） | 报价单缺失是真问题（销售流程的起点），但**打印模板编辑器是低 ROI**——用 PDF 模板 + 字段插值即可。**优先级：报价单 P1、打印编辑器 P3** |
| 8 | **月度考勤矩阵 + 日报双视图** | 16:53-17:07 | UI 很漂亮（员工×日历颜色编码：正常/请假/旷工/加班）。Cretas 有 TimeClock 但**没这个汇总视图**。客户提到"管理层在做数据"——这种汇总视图正是给管理层看的。**优先级 P2** |
| 9 | **同产品 × 多客户价目表**（历史价记忆） | 10:42 | 食品行业谈判常态。**优先级 P2** |
| 10 | **工作手机/微信会话归集**（22:28） | 22:28 | 宏见标为"**增值业务**"——意思要单独收费。**这其实是合规边界灰色地带**（业务员的微信会话上传到系统主），不一定每个客户都接受。**不建议抄** |

### 🔴 第三档：不要抄 (会拖累 agent 范式)

| # | 功能 | 为什么别抄 |
|---|---|---|
| 11 | **左侧 12 模块菜单（客户/销售/采购/仓库/财务/生产/嵌件/工程/品质/人事/OA/系统）** | 这是 1990s ERP 范式。Cretas 已经走了"场景化入口 + AIChat 触发"的现代路线。**为了对齐功能加菜单 = 倒退** |
| 12 | **角色权限可视化页**（如 16:13）| Cretas 已有完整 RBAC + canViewPrice 多视图权限，比宏见的"绿色权限块"细得多。**别学倒车** |
| 13 | **按统计员批量录入员工报工** | 客户当场表达不满意。这是"没有视觉识别所以只能这样做"的产物。Cretas 应该用摄像头视觉识别报工**绕开**这个范式（详见 §D-2） |
| 14 | **节点单据强制流转**（请购→采购→出货→入库 N 单据流程） | 这是客户最大抱怨："那个论证在论的太多了"。**Agent 范式的核心就是替用户把这些单据流编排好**，不是给用户看 7 个单据让他自己走流程 |

## C. 客户购买决策的胜负手 — 这是最关键的部分

### 客户原话 (16:50-21:30)
> "适配性比较高……**但目前看下来咱们咱们那个系统的那个论证在论的太多了，成四个部门，我看能不能一定适应**，而且这个如果按你这个流程走的话，**我们就是整体的操作流程可能要更改一下**……所以我还是找他们要碰一下，**这个暂时没办法给你直接回复**。"

### 解码
1. "**论证太多**" = 单据流程层级太深，从销售到入库要走 7-8 张单据
2. "**操作流程要更改**" = 客户必须改自己的业务流程去适应宏见 ERP，**不是反过来**
3. "**暂时没办法回复**" = 委婉拒绝，要内部讨论 (实际意思 = "我感觉别扭，要找借口推掉")

### 宏见的应对失败
- 销售只能用"全功能版本砍掉 X 模块" 的方式降低复杂度——这是**产品复杂性的妥协**而不是解决
- 销售反复说"线下派授权"——把决策推给下次见面，但客户在拖延

### Cretas 的杀手锏 (这一节决定能不能赢这单)

**核心命题**：传统 ERP 把"流程"当作产品的一部分卖给客户；Cretas 把流程留给客户自己说。

具体差异化话术（如果给客户演示 Cretas）：
1. "您不需要学我们的单据流程。您怎么说我们怎么做。"
2. "您的车间老员工不需要打开手机操作。摄像头看到他到岗就自动报工。"
3. "您发现库存低了不需要去查报表。系统会主动告诉您该补货。"

这三句话每一句都是 Cretas 已有的技术（AIChat / ISAPI / AlertScreen），但 **Cretas 团队对外没这么讲过**。

## D. Cretas 真实评分 (不留情面)

### D-1. 客户在意但 Cretas 真有差距的 (P0)

| 项 | 真实差距 | 影响 |
|---|---|---|
| **统一缺料分析视图** | 后端零件齐但没整合 UI | 销售要去开 3 个页面建 3 张单 |
| **生产任务 QR** | LabelScan 组件在，但生产任务没生成 QR | 工人无法快速对应任务 |
| **领料单创建时按 BOM 自动填** | BomExpansionTool 在，未接到前端 | 录入慢 5-10 倍 |
| **报价单实体** | 完全缺失 | 销售前置流程断 |

### D-2. 客户在意，Cretas 已有但**没卖**的 (P0 — 主要是营销问题)

| 项 | 实际状态 | 为何客户感受不到 |
|---|---|---|
| **AIChat 对话式 ERP** | 8 场景 × 337 工具 × 16 技能，已可用 | 演示流程仍按"打开模块→建单"路径走，没体现 agent 价值 |
| **摄像头视觉识别** | ISAPI/Dahua/Hikvision 全栈，行为识别已有 | 没把"自动报工"作为演示重点 |
| **食品溯源全链路** | TraceFullTool/TraceBatchTool 都在 | 食品厂客户对溯源敏感（盒马/山姆审计要求），但 Cretas 没主推 |

### D-3. 客户暂不在意，Cretas 也确实缺的 (P2-P3)

- 会计凭证模板系统
- 可视化工作流编辑器
- 工作手机微信集成
- 多客户历史价记忆

## E. Agent 简化方案 — 可信度评估

> 原报告给了 5 个方案，但没说"哪些真能 hold 住客户"。这里做实评。

| 方案 | 是否真能落地 | 可信度 | 备注 |
|---|---|---|---|
| **1. 一句话销售→生产→采购全链路** | ✅ 真能 | 🟢 高 | 已有 90% 零件 (ShipmentCreateTool/BomExpansionTool/SupplierRankingTool 等 9 个 Tool)，需要的是新 SalesToProductionSkill 编排 + RichContentRenderer 加 chain-card 类型。**这是 Cretas 当前最大未被讲出来的优势** |
| **2. 摄像头视觉自动报工** | ⚠️ 部分能 | 🟡 中 | ISAPI 区域检测 + 工人识别已有，但**没在真实工厂跑过 8 小时持续报工**。需要先做 PoC：选客户工厂的 1 条产线试 30 天，看准确率能否 ≥ 90%。**别拍胸脯说能做好** |
| **3. 异常驱动而非主动查询** | ✅ 真能 | 🟢 高 | AIAlertsScreen + AlertTriageTool 都有，只是推送密度太低。**3-5 天工作量调密度** |
| **4. 多轮对话 slot-filling** | ✅ 真能 | 🟢 高 | NEED_CLARIFICATION 路径在 AIChatScreen 已有，只需把所有 create-Tool 的 slot 定义补全 |
| **5. 智能默认值 + 模板** | ✅ 真能 | 🟢 高 | smartDefaults.ts + TemplateCommandSheet 已经在，扩展模板类型即可 |

**结论**：5 个方案里 4 个是"3-5 天工作量就能放大现有能力"，**只有视觉报工真有技术风险**。这对销售意味着：**4 个可以立刻在 demo 视频里展示，1 个标"PoC 阶段"**。

## F. 我的优先级建议 (含反对意见)

### 立即做 (本月)
1. ✅ **写一个 SalesToProductionSkill** + 在 AIChatScreen 加 chain-card 渲染 — 2 周
2. ✅ **生产任务列表加 QR 列** + 扫码后路由到 BatchReport(taskId) — 1 周
3. ✅ **录一段 Cretas 销售 demo 视频**：用上面两个能力，演示"销售员说一句话完成宏见 5 个页面的工作" — 0.5 周

### 短期 (1-2 月)
4. ✅ **领料单按 BOM 自动展开**（中 3 人天） — 跟宏见对齐基础体验
5. ✅ **统一缺料分析视图**（5-7 人天） — 这是抄宏见最有价值的一项
6. ✅ **补全 create-Tool slot 定义** + 推送密度提升 — 让 AIChat 覆盖更多场景

### 中期 (3-6 月)
7. ⚠️ **视觉报工 PoC**：选 1 个食品厂客户、1 条产线、3 个月跑数据
8. ✅ **报价单实体 + 模块**（销售流程前置）
9. ⚠️ **会计凭证模板**：仅当目标客户群中 ≥30% 要求时再做

### 我反对做的
- ❌ **可视化工作流拖拽编辑器** — 这是 PR-driven 工程，让 IT 喜欢但用户不用。已有 ApprovalChainConfig + AIChat 配规则就够了
- ❌ **左侧 12 模块菜单** — 倒车
- ❌ **工作手机微信集成** — 合规风险 + 与 agent 范式无关
- ❌ **强行追平宏见所有功能** — 我们的胜负手是"少做单据 + 多做对话"，不是"功能数量对齐"

### 我反对的"团队潜在冲动"
- 看完竞品演示，团队往往想"全部抄一遍证明我们也行"。**这是给自己挖坑**。竞品的功能列表是它过去 10 年的累积，我们若要 6 个月追平就会变成它的劣化版
- 重点是**做我们已经做的更好**：把 AIChat + ISAPI + 食品溯源讲清楚演明白，不是去抄它的菜单结构

## G. 销售/对接层面的额外发现

观察客户的购买决策路径（音频 18:35-21:30）：
- 客户主动报上工厂规模（"生鲜 + 冷冻牛肉，盒马山姆卡斯克，24 小时生产，7-8 万人……"）—— **客户口误说"7-8 万人"，宏见销售没追问**，错失"真实工厂规模 = 销售关键信息"
- 客户问试用账号 → 宏见用"派授权(销售经理)线下"延迟回应 — **是宏见的销售流程导致**，不是客户不愿意
- 客户当地是苏州/昆山，宏见有当地分公司 → 但客户说"不方便见面，先线上聊" — **客户在防御**

如果是 Cretas 销售：
- 应当**立即追问**"7-8 万人是您所有工厂总和，还是某一个车间？" — 这决定了 SaaS 报价
- 立即给试用账号，让客户在自己时间体验，AIChat 是天然的"无门槛 demo"
- **不要派人下去**，反而把"远程 onboarding by agent"做成卖点

## H. 复盘：我作为 AI 助手在本任务上的不足

为了诚实，记录原 REPORT 的失误：

1. **抽帧密度不够**（0.15 阈值漏了 14:35-16:53 段的 3 个关键页面：财务凭证模板、角色权限、考勤矩阵）
2. **报告偏总结**（每段都讲了演示了什么，但没说"Cretas 该怎么做")
3. **方案可信度未评**（5 个 agent 方案放一起，没区分哪些有技术风险）
4. **没识别销售决策路径**（客户拒绝信号在 16:50 已经清楚，原报告未捕捉）
5. **没给反对意见**（团队看了全是"该做"，没有"别做"——这会导致 scope 失控）
