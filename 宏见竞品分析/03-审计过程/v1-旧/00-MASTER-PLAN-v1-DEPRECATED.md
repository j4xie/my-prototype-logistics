## 第一章 执行摘要

### 1.1 项目背景

**素材来源**:
- 宏见武汉销售给苏州/昆山食品厂的腾讯会议演示 (23:32 HD 录屏 + 21:36 音频)
- Cretas 真实客户**六扇门 F006 卤制品工厂** 4 次会议记录 + 研发样品至财务回款全流程文档

**审计深度**:
- 6 轮迭代审计 (REPORT → REVIEW → AUDIT → TRUTH_AUDIT → REVISED_STRATEGY → MUST_COPY)
- 4 路并行 fresh-eyes 子代理审计 × 多次
- 137 张 HD 关键帧 + 251 段音频 + 全代码库 grep 验证

### 1.2 核心发现 (5 条)

**1. 客户不要传统 ERP, 客户要 AI-First Hybrid ERP**
> 客户第二次会议原话: "我们不再想开发那种传统的那种 ERP 了, 那个东西我们已经试过 3-4 次了 (含金蝶), 都不完美, 最后用不起来"
>
> 客户主动要求: "底层 ERP + AI 做中间桥梁"

**2. AI 一句话替代是浪漫主义**
- 业务流的合规性不可压缩 (审批/角色/状态机/审计追溯)
- AI 真替代仅 **12.2%** (远低于乐观估计 50%)
- **Hybrid (UI 主 + AI 辅) 占 46.9% 是常态**

**3. Cretas 真实能力比之前认知更强**
- AI Tool **404 个** (之前说 337, 低估 67)
- Skill **32 个** (18 内置 + 14 SKILL.md, 之前说 16)
- **35+ 餐饮专用 Tool** 是独家壁垒 (V2_HD 没识别)

**4. Cretas 有 4 处死代码 + 5 处半成品 bug**
- AILayoutAssistant 是假 AI (rule-based 写死)
- PageEditor 1252 行 dead code (no nav)
- AIChat 多轮 sessionId 不传
- Canvas Tool 写错 Repository
- 5 个客户测试发现的 bug (三价对比 / 工序通用 / PDF 串通 / BOM 选择器 / 单位转换)

**5. 文档体系混乱, 23 处不一致**
- "嵌件管理" vs "委外管理" 在 4 份文档没改
- S1 工时跨文档差 3-15 倍
- GAPS.md 23 条 12 条被证伪未改写

### 1.3 行动决策 (3 条)

**决策 1: Phase 0 立即修死代码 (10 人天)**
- 不修这 4 项, 任何 demo 都会翻车
- 修完后销售红线全部解除

**决策 2: 必抄 18 项业务功能 + 23 项 UI/UX (~145 人天)**
- 三重过滤后: Cretas 真缺 + 客户真需要 + AI 替代不了
- 比之前估计的 220 人天压缩 35%

**决策 3: 演示路径改为"完整业务流 + 每步 AI 增强"**
- 不是 "AI 一句话替代", 而是 "保留单据流 + AI 录入/查询/感知优化"
- 10 分钟 demo 覆盖客户 80% 关心

## 第二章 客户画像与真实需求

### 2.1 客户基本信息 (六扇门 F006)

| 维度 | 详情 |
|---|---|
| 公司类型 | 食品加工厂 (卤制品 + 冷藏生鲜 + 冷冻牛肉) |
| 工厂位置 | 苏州 / 昆山 |
| 业务 1 | 生鲜冷藏 → 盒马 1-2 万份/天 |
| 业务 2 | 冷冻牛肉 → 山姆 / Costco 400-1000 箱/天 |
| 生产模式 | 7×24 无尘车间, 24 小时生产 |
| 人员规模 | 前期 30-50 人用系统, 操作工 ~ 千人级 |
| 主要部门 | 销售 / 采购 / 仓库 / 生产 (4 部门, 不是 12) |
| 员工特征 | 操作工年龄大 + 文化素质偏低 |

### 2.2 客户已经放弃 3-4 次传统 ERP

第二次会议原话 (2026-03-18):
> "数字化这个事我们也研究好几年了, 但一直没有说非常好, **落地之前自己也做过几个版本, 也用过这个外面的这个金蝶什么的系统**, 最后都特别难落地"
>
> "今天就是想探讨一个问题啊, 呃, **我们不再想开发那种传统的那种 ERP 了**, 那个东西我们已经试过 3-4 次了, 就是无论开发都不完美, 最后用不起来"

**失败根源** (客户自述):
1. 非标品多 SKU + 辅料管理痛苦 (一个熟食 30-40 种辅料, 用量极低)
2. 字段太严谨, 录入繁琐
3. 每天为了几克辅料浪费大量人力维护

### 2.3 客户对 AI-First 的明确期望

第二次会议原话:
> "想用 AI 这个应用进去, 帮我们做一个**中台的数据调度**"
>
> "员工的互相交互, 就跟这个大模型来交互, 比如说我们告诉他说**好, 现在我这个 GPS 牛腩入库 42 件**, 日期是多少, **或者拍个照给他**, 然后他就自己把这条信息就是写进去"
>
> "我们想要这个提取信息的时候也就跟他要说, **你给我查一下现在订单有多少件啊, 然后拉一个表格给我**"

**客户的 AI 期望具体场景**:
- ✅ 自然语言录入: "GPS 牛腩入库 42 件" / 拍照
- ✅ 自然语言查询: "现在订单多少件"
- ✅ 钉钉机器人作为交互入口
- ✅ AI 帮忙做中台数据调度
- ❌ 不是要替代业务流程本身

### 2.4 客户业务全流程 (7 大模块, 不可压缩)

来自《研发样品至财务回款全流程文档》:

```
1. 研发样品 → BOM 生成 → 报价推送
   (销售/研发/审核人/报价员 4 角色)
        ↓
2. 销售订单 → 财务成本核算审核
   (销售/财务 2 角色, 三价同屏)
        ↓ (审核通过自动分流)
3. 缺料分析 → 采购订单 → 财务采购审核
   (采购/财务 2 角色, 三价标红预警)
        ↓
4. 采购到货 → 仓管员扫码入库
   (仓管员只录: 收货数量 + 商品日期 + 拍照附件)
        ↓
5. 生产任务 → 工序拆解 → 领料 → 完工入库
   (工人扫码 + 累加报工)
        ↓
6. 销售出库 → 送货单
   (销售/仓库 2 角色)
        ↓
7. 开票申请 → 开票回传 → 收款流水
   (销售/财务 2 角色)
```

每一步都有**明确角色 + 状态机 + 审批 + 审计追溯**。Agent 不能跳过任何一步。

### 2.5 客户 UX 哲学 (核心原则)

第三次会议 Part 2 原话:
> "做仓管的他**年纪都比较大文化素质很低的**, 你**不能太伪赖他们**, 最好的方法就是你告诉他**这个东西你要收多少就行了**, 就**越写呢越越减少出错**"
>
> "做仓管的任务很简单: **核对数量 + 核对商品日期 这两个**"
>
> "**价格类的不要让他们去参与**"

**翻译为设计原则**:
- 每个角色**最少必要操作**
- **字段越少越好**
- **能扫码不要键盘**
- **能拍照不要打字**
- **价格类不让仓管碰** (角色隔离)

### 2.6 客户对 Cretas 现状的具体反馈 (4 次会议提取)

✅ **已认可** (第三/四次会议):
- 一二级单位转换 g↔kg "你做的挺好的"
- 销售单价 BOM 默认 + 可改
- 三价对比 "近期价" 来源
- 默认 FIFO 出库逻辑

⚠️ **已反馈但未修** (10 个具体 bug/缺口):
1. PDF 打印 + 扫码入库 RN 端 UI 未串通
2. RBAC 采购员/仓管员严格隔离审计 (审验 #423 完整性)
3. 收货数量分次显示列 ✅ 已 ship (#414)
4. 生产工序"通用 P 过来"未关联 bug
5. 预估成本字段权限隐藏 (财务争议)
6. BOM 物料名称改为选择 (不是手写)
7. 单位转换强校验
8. 钉钉机器人 PoC (战略级需求)
9. 列宽 audit ✅ 已 ship (#535)
10. 三价对比新建后不刷新 bug

| 卖点 | 客户反应 |

### 3.3 宏见的真实弱点 (销售自承 + 客户没接受)

**销售自承** (17:51, 帧 `001806`):
> "**装箱称重 / 设备管理 / 模具 这些不一定用, 可以去掉**"

→ **承认产品过载, 没有行业精专**

**客户没接受**:
1. **"论证太多, 成 4 部门"** = 12 模块对客户 4 部门过载
2. **"操作流程要更改"** = 客户要适配宏见, 不是宏见适配客户
3. **"暂时没办法给你直接回复"** = 委婉拒绝, 缓议

**销售失败证据**:
- 8 步销售流程 (线上 demo → 派单 → 上门 → 砍功能 → 样板 → 报价 → 试用 → 签约) 当前**阻塞在 Step 2→3**
- 客户拒线下访谈, 要 "先线上聊"
- 销售自称"我只是接线员", 13 次推卸到"派授权"
- **录音里 0 个成交/试用信号**

### 3.4 客户决策路径解码

客户讲冷链/商超/24h 生产/30-50 用户期间, 屏幕停在**设备管理**(数控机床) **5 分钟**。销售自己在 17:51 也说 "装箱称重 / 设备管理 / 模具不用可以去掉"——**但此刻还停在这些页面没切走**。

→ **直接证据**为什么客户说"系统像机加工不像食品": 不是功能缺陷, 是**信息架构暴露问题** + **销售员没行业敏感度**。

### 3.5 宏见的传统范式总结

| 维度 | 宏见做法 |
|---|---|
| 整体设计语言 | 1990s 密集 Web 表格 + 浮动菜单 |
| 录入入口 | 表单 + 字段严谨 |
| 查询入口 | 17 列报表 + 17+ 筛选 |
| 异常感知 | 用户主动查报表 |
| 流程触发 | 进单据 → 点按钮 |
| 录入门槛 | 50+ 字段, 必须开页面 |
| 培训成本 | 1-2 周学单据流 |
| 多语言 | 仅中文 PC Web |
| 行业精专 | 通用 ERP, 客户砍功能 |
| AI | 0 |

## 附录 A: 元层学习

1. **真实客户档案 > 竞品分析** — 4 次会议 > 137 帧视频
2. **HD vs 压缩源差 15 倍信息密度** — 微信压缩导致误读 10+ 处
3. **"AI 替代 UI" 是 PR 话术** — 业务流合规性不可压缩
4. **"实体存在"≠"功能可用"** — Label 有 QR ≠ 生产任务能生成 QR
5. **每次声明都要 file:line 证据** — Subagent 表面扫描会误判
6. **Subagent 多轮 fresh-eyes 才能找全** — 单轮会漏 / 误判 7 处
7. **文档不 retire 会污染团队认知** — 13 份 23 处不一致
8. **下次竞品分析必须先查客户档案** — 客户档案优先级最高
