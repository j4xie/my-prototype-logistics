## Test Results

### R70-FIX-D — ProcessTask quantity guard (R69-BUG-2 fix)

**Code change**: `ProcessWorkReportingServiceImpl.syncQuantitiesToTask` (lines 463-501)

Pre-fix:
- No upper bound — `task.setCompletedQuantity(current.add(quantity))` blindly accumulated
- No CLOSED state guard — silently wrote to closed tasks
- pt-001 actual state: plannedQuantity=100, completedQuantity=1178 (10× over-completion observed)

Fix:
- **Guard 1**: if task.status == CLOSED → throw BusinessException(409) "工序任务已关闭, 不可继续报工同步" + actionHint "请刷新报工列表, 该任务已关闭, 不允许新报工" + hintTarget "processTaskId"
- **Guard 2**: if newCompletedQuantity > plannedQuantity × 1.10 → throw BusinessException(409) with detailed message about overshoot + actionHint "请检查计划数量, 或拆分为多次报工" + hintTarget "outputQuantity"
- 1.10 multiplier is industrial-realistic 10% over-production tolerance
- Both throws inside @Transactional, so rollback report.approvalStatus too (caller approve()/batchApprove() are @Transactional)

**Real-window verify on test 8097**:
1. Found clean ProcessTask `e8166bb1-...` (planned 30, completed 0, status PENDING)
2. Submit qty=20 report → submitNormalReport returns 200, taskStatus auto-transitioned to IN_PROGRESS, pendingQuantity 0→20
3. Approve report (id=533) → 200 success
4. **Cross-table verify (R70-FIX-A)**: re-GET ProcessTask → status=IN_PROGRESS ✓, completedQuantity 0→20 ✓, pendingQuantity 20→0 ✓
5. **Overshoot test**: submit qty=15 report (would push 20+15=35 > 30×1.10=33), then approve → HTTP **409** + message "本次报工 15.00 会让累计完工 35.00 超出计划 30.00 的 110% 上限 (cap=33.0000)" + actionHint "请检查计划数量, 或拆分为多次报工 (每次不超出 cap)" + hintTarget "outputQuantity" ✓

This is the **first true L4 deep test in the R67-R70 chain** — Rule 11 §3 三行 (filled DTO + toast captured via API status + list-after re-GET) all met.

### R70-FIX-C — backend race-condition probe
