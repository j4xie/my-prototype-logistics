## R71-FIX-B — UI DOM double-click probe

### Test design (Rule 11 §3 + R23 BUG-6 / R41 BUG-6 lineage)

1. Login as factory_admin1 → `/production/approval` (queue 127 pending)
2. Set up MutationObserver on `document.documentElement` (R69-BUG-3 fix — survives SPA routing)
3. Find first `<button>通过</button>` element
4. Dispatch 2 click events with 30ms gap (faster than human reaction time)
5. Wait 2.5s for both responses
6. Capture `.el-message` (toasts) + `.el-notification` (sticky) DOM additions

### Result (PASS)

| Capture | Content |
|---|---|
| `.el-message--success` (auto-dismiss) | text=**"已通过"**, closable=false |
| `.el-notification` (sticky) | heading=**"操作无法完成"**, body="报工记录已被处理，当前状态: APPROVED 请刷新报工列表查看最新审批状态", closable=true |
| Visible toasts after 2.5s | 1 success + 1 sticky 409 |
| Queue delta | 127 → 126 = exactly 1 approve |

### Verdict

**🎉 GOLDEN behavior** — UI handles double-click correctly:
- First click → backend approves report → success toast
- Second click 30ms later → backend 409 (state-conflict from R39 BUG-9) → axios interceptor
  in `web-admin/src/api/request.ts:344-353` differentiates between vanilla optimistic-lock 409
  (suppressed) and BusinessException-with-actionHint 409 (rendered as sticky ElNotification)
- No double-success toast (interceptor.actionHint suppression vs differentiation works)
- No silent failure (the 409 surfaces visibly via ElNotification)
- Data consistency: only 1 approve persisted (backend transaction won race exactly once)

This validates 3 stacked safety mechanisms:
1. **Backend race handling** (R70-FIX-C verified earlier): DB-level locking + idempotency check
2. **Backend error contract** (R67-FIX-1): typed BusinessException(409).withHint() returns rich payload
3. **Frontend interceptor differentiation** (Bug #312 / R24 fix): renders BusinessException 409
   as ElNotification (sticky+closable), suppresses vanilla optimistic-lock 409
