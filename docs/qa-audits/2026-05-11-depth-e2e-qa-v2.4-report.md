## P1 BUG-1 (FAIL): Semantic-mismatch on CREATE/UPDATE FK violations

### Reproduction (T1.11 + T6)

POST `/api/mobile/F006/transfers` with `targetFactoryId: "TEST_TARGET_FACTORY"` (non-existent):

- Backend response (409):
  ```json
  {
    "success": false,
    "code": 409,
    "message": "无法删除: 该数据仍被其他记录引用",
    "actionHint": "先处理引用该数据的相关记录后再删除",
    "severity": "warning"
  }
  ```
- UI toast (MutationObserver-captured):
  ```
  cls: el-notification right ...
  text: 操作无法完成无法删除: 该数据仍被其他记录引用\n\n先处理引用该数据的相关记录后再删除
  hasCloseBtn: true
  ```
- Rule 8 four-tuple result: **a=b**, **sticky=yes**, **specific=yes** — UX layer is technically correct.
- **But semantically WRONG**: message says "无法删除" / "先处理引用该数据的相关记录后再删除", but the HTTP method is **POST (CREATE)**, not DELETE. User reading this on a CREATE form thinks "did I create something already? do I need to delete it first?" — completely confusing.

### Root cause (verified via source)

`backend/java/cretas-api/src/main/java/com/cretas/aims/exception/GlobalExceptionHandler.java:467-476`:

```java
} else if (isFkViolation) {
    // 尝试从错误消息提取被引用的目标表, 给用户清晰线索
    message = "无法删除: 该数据仍被其他记录引用";
    actionHint = "先处理引用该数据的相关记录后再删除";
    java.util.regex.Matcher m = ...
}
```

This handler fires for **any** PostgreSQL FK violation, regardless of HTTP method. The wording assumes DELETE op (which is the most common case where FK violations matter — orphaning child records). But INSERT and UPDATE can also violate FK if a referenced FK target doesn't exist (e.g., creating a transfer with non-existent target factory).

### Affected endpoints (impact assessment)

Any POST / PUT endpoint where the service layer does NOT pre-validate FK fields and lets the DB constraint surface up. Conservatively:

- `POST /transfers` (target factory) — confirmed P1
- `POST /sales-orders` (customer + product)
- `POST /purchase-orders` (supplier)
- `POST /production-plans` (product type) — may have service-layer guard
- `PUT /material-batches/{id}` (supplier change to invalid)
- `POST /receipts` (purchase order ref)
- (~18-20 endpoints in total based on FK usage in entity classes)

Some endpoints (e.g., `POST /material-batches` per T6) have **service-layer pre-validation** that throws a proper specific message ("原材料类型不存在") before the FK constraint can fire — those are immune. The bug surfaces only on endpoints that rely on DB FK to surface up.

### Recommended fix

**Option A (preferred — narrow & exact)**: in `GlobalExceptionHandler.handleDataIntegrityViolation`, detect HTTP method via `RequestContextHolder` and emit context-appropriate message:

```java
HttpServletRequest req = ((ServletRequestAttributes)
    RequestContextHolder.currentRequestAttributes()).getRequest();
String method = req.getMethod();
if ("DELETE".equals(method)) {
    message = "无法删除: 该数据仍被其他记录引用";
    actionHint = "先处理引用该数据的相关记录后再删除";
} else {
    message = "操作失败: 引用的关联数据不存在";
    actionHint = "请检查表单中关联的工厂/客户/物料等是否存在";
}
```

**Option B (orthogonal)**: each affected service should pre-validate FK references before calling repository.save(), throwing a specific `BusinessException(400, "目标工厂不存在: " + targetFactoryId)`. Better UX but spread across 20+ services — higher cost.

Estimated PR scope: Option A is ~30 LOC change + 4-6 unit tests in `GlobalExceptionHandlerTest`. Customer-visible impact: 18-20 endpoints get clearer error messages immediately.

## P2 BUG-2 (WARN): `/factories/network` returns 401 for f006_admin

### Reproduction (T1 console errors + network log)

`GET /api/mobile/F006/factories/network` returns:
```json
{
  "code": 401,
  "message": "用户未登录",
  "actionHint": null,
  "severity": null,
  "data": null
}
```

But the user IS logged in (other endpoints return 200). Likely cause: this endpoint expects a different auth scope (e.g., requires `factory_network_read` permission that f006_admin doesn't have), but returns generic 401 instead of 403 with proper message.

A "用户未登录" toast appears in the page header on transfer page load (T1 screenshot t1-02-dialog-open.png top-right red badge), but the user is clearly logged in.

### Affected paths

- `/transfer/list` (loadFactoryNetwork() in transfer/list.vue:114)
- Any future page using `/factories/network`

### Recommended fix

- If permission-based: return 403 with "无访问该资源的权限: 需要 factory_network_read"
- If logic-based (no network configured for F006): return 200 with empty array + actionHint "本工厂未配置工厂网络, 请联系总部"
- Frontend: filter out 401 from `/factories/network` specifically (it's a graceful-degradation fallback per code comment line 121: "Fallback: at minimum let user fill in manually")

## P2 BUG-3 (WARN): BOM service accepts `standardQuantity: 0`

### Reproduction (T3 POST body)

POST `/api/mobile/F006/bom/items` with body:
```json
{
  "id": null,
  "materialTypeId": "",
  "standardQuantity": 0,
  "yieldRate": 58,
  "unit": "g",
  ...
}
```

Backend response: 200 OK, item created with ID=31. But `standardQuantity=0` BOM item is meaningless (0g of material can't produce anything).

### Recommended fix

`BomService.saveBomItem()` should validate `standardQuantity > 0` and throw `BusinessException(400, "标准用量必须大于 0")` with `actionHint: "请填写标准用量后保存"`. Also reject empty-string `materialTypeId`.
