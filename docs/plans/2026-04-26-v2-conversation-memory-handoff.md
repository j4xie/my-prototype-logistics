## 2. 核心问题: 无对话记忆 → follow-up 退化

### S3 audit 实证

**5 类 follow-up 综合得分**:
- 趋势 (trend): 3.45/5 — 最佳, trend 模板复用率高
- 对比 (compare): 3.32/5 — Top N 模板能算差距
- 假设 (what-if): 3.18/5 — LLM 兜底但缺数据时仍能定性预估
- 怎么办 (action): 3.15/5 — 需 main context 才能给具体 action
- 为什么 (why): 2.98/5 — **最差**, 需根因分析无 main 锚点 LLM 只能猜

### 典型失败案例 (cite from audit)

**F1 — xmx-fu-15-1 "流失会员的主因是什么"**:
- bucket: llm_cold (30s) timeout, 0 字答案
- 需要 context: main xmx-15 已暴露 "60,003 会员 + 当前余额 0.84/人 → 推测大量沉睡". 有此 context, FU 立即给"流失原因 = 余额耗尽未召回".
- **没 context, LLM 30s 等死**

**F2 — qhj-fu-13-1 "哪个维度评分最低 为什么"**:
- bucket: llm_cold (26s) 空答案
- 需要 context: main qhj-13 cache hit "评价数据汇总", 已有 "口味4.82/环境4.82/服务4.83". FU 没看到所以重新计算 → timeout.

**对比典型成功 W2 — gml-fu-01-2 "如果停售 Top 1 影响多大"** (28s, llm_cold):
- "Top 1商品(编码103028120000)销售金额为**4,386,049.00元**, 占总销售金额88,696,414.90元的**4.94%**. 停售将直接减少约4.94%的销售额."
- LLM 用 main 已暴露的 Top 1 数字做精确占比 — 因为 LLM 自己**重新生成**了相似分析, 但每次都得花 28s

**用户痛点**: 每个 follow-up 都从零开始, 大表全扫, 信息冗余, 时延翻倍.

## 3. v2 设计方案 (Plan A — lightweight context, 推荐)

### Architecture

```
┌──────────────────┐       ┌──────────────────────────────┐
│ Frontend / Java  │  POST │ /api/chat/general-analysis-  │
│                  │ ────▶ │ stream                       │
│ session_id?     │       │ + session_id (optional)      │
│ + query          │       │ + query                      │
└──────────────────┘       └────────┬─────────────────────┘
                                    │
                          ┌─────────▼──────────┐
                          │ Phase 0:           │
                          │ session lookup     │
                          │ (Postgres table)   │
                          └─────────┬──────────┘
                                    │
                  ┌─────────────────┼─────────────────┐
                  ▼                 ▼                 ▼
         No session_id      Found session       Session expired
         → standalone       → load parent       → standalone +
         (current path)     summary             new session
                            ↓
                      ┌─────────────────────────┐
                      │ Inject context into     │
                      │ LLM prompt:             │
                      │   "上一回合: [summary]"  │
                      │   "本轮提问: [query]"    │
                      └────────┬────────────────┘
                               ▼
                      [existing pipeline]
                      (template / cache / LLM)
                               ▼
                      ┌─────────────────────────┐
                      │ After answer: update    │
                      │ session.last_answer_    │
                      │ summary (truncate to    │
                      │ 500 tokens)             │
                      └─────────────────────────┘
```

### DB Schema

```sql
CREATE TABLE smart_bi_chat_session (
  id            BIGSERIAL PRIMARY KEY,
  session_id    VARCHAR(64) NOT NULL UNIQUE,  -- UUID, generated by FE on session start
  factory_id    VARCHAR(50) NOT NULL,
  user_id       BIGINT,                       -- nullable (anonymous mode)
  parent_query  TEXT,                          -- last main query in this session
  parent_answer_summary TEXT,                  -- truncated to ~500 tokens
  parent_template_code  VARCHAR(100),          -- if cached, which template
  parent_upload_id      BIGINT,                -- which upload was used
  turn_count    INTEGER DEFAULT 0,             -- how many turns in this session
  created_at    TIMESTAMP DEFAULT NOW(),
  updated_at    TIMESTAMP DEFAULT NOW(),
  expires_at    TIMESTAMP DEFAULT NOW() + INTERVAL '1 hour'
);
CREATE INDEX idx_chat_session_factory ON smart_bi_chat_session(factory_id);
CREATE INDEX idx_chat_session_expires ON smart_bi_chat_session(expires_at);
```

### Implementation steps (2 day)

**Day 1 morning** (~3 hr):
- DB migration (Flyway)
- ChatSession model + Repo
- /general-analysis-stream 接 `session_id` query param (optional)
- Phase 0: lookup session, populate `request.state.session` if found
- Update logic at end of stream: write parent_answer_summary

**Day 1 afternoon** (~4 hr):
- Prompt builder: when session found, prepend "上一轮提问: {parent_query}\n\n上一轮回答: {parent_answer_summary}\n\n---\n\n本轮提问: {query}"
- Token budget: limit summary to 500 tokens via `tiktoken` count + truncate
- Test 6 follow-up scenarios manually (qhj-fu-15-1 / qhj-fu-13-1 / gml-fu-01-2 / xmx-fu-15-1 + 2 controls)

**Day 2 morning** (~3 hr):
- Frontend changes: AIQuery.vue 持久化 session_id (sessionStorage), pass to backend
- Conversation reset button (clears session_id)
- TTL cleanup cron (DELETE expired sessions every 30 min)

**Day 2 afternoon** (~3 hr):
- E2E test: re-run S3 270 follow-ups with session continuity
- Audit (agent-team) for delta vs P5
- Commit + deploy

### Cost analysis

- LLM prompt token 增量: avg +500 token (parent summary) → DashScope ¥0.0015/1K = ¥0.00075/query
- 270 follow-ups × ¥0.00075 = ¥0.20/batch
- 加上更多 LLM tail 不再 timeout (因为有 context, LLM 不用从零分析): -10% LLM cold time → 实际成本可能持平甚至下降
- DB write: 1 row per turn, negligible

### 期望影响 (S3 audit 推算)

- S3 整体 3.21 → **3.6+** (+0.4)
- 为什么 类 2.98 → **3.5+** (+0.5, 最大受益, 因为根因分析需 main context)
- 怎么办 类 3.15 → **3.6+** (+0.45)
- timeout/empty 11.5% → **<5%** (有 context LLM 不再迷茫)
